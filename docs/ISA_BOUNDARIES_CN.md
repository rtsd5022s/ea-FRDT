# 处理器指令集性能边界

## 一、为什么指令集决定浮点性能天花板

浮点计算的速度不是由 CPU 主频单独决定的。同样一颗 3.4GHz 的 i7-6700，跑标量 `addss`（标量单精度加法）每秒大约能做 3.4 亿次运算，但跑 AVX2 的 `vaddps`（256 位向量加法，一次 8 个 float）理论峰值能到 27 亿次。差 8 倍，不是因为主频变了，而是因为指令集一次能塞进执行单元的数据宽度变了。

ea-FRDT 测量的不是吞吐率，但它走路的步数受两个因素影响：一是格式本身的位宽决定了每步算术的复杂度，二是 CPU 的指令集决定了这种算术能跑多快。一个纯软件仿真的 FP128（112 位尾数，224 位乘法中间结果）在没有 128 位浮点硬件的 CPU 上，只能靠整数寄存器慢慢移位累加，和一个原生支持 AVX-512 的 CPU 跑 FP32 相比，速度可能差几百倍。

本文档梳理从 8087 到最新 AVX-512、从 x87 到 ARM SVE2 的浮点指令集演进，以及它们在边界测试中表现出的性能天花板和陷阱。

## 二、x87：第一个浮点协处理器的遗产

1980 年的 8087 是 x86 浮点的起点。它有 8 个 80 位寄存器（堆栈结构），原生支持 80 位扩展精度（64 位尾数，15 位指数）。这就是为什么今天的 x86 CPU 仍然有 x87 模式——它不是为了兼容性，而是因为 80 位扩展精度在某些场景下仍然有价值。

x87 的性能边界：

- **80 位寄存器**：比 IEEE 754 binary64 多了 15 位尾数和 3 位指数。这意味着中间计算可以保留更多精度，减少舍入误差。但代价是 x87 是堆栈寄存器，不是寄存器堆，编程模型受限。
- **微码模拟**：在现代 CPU 上，x87 指令大部分是微码实现，不是硬连线执行单元。一个 `fadd` 的延迟可能比 `addsd`（SSE2 双精度加法）还高。
- **没有向量**：x87 一次只能做一个 80 位数的运算，没有 SIMD。8087 时代没有向量概念。
- **状态字**：x87 有一套自己的异常标志（精度下溢、上溢、除零、无效操作），和 SSE/AVX 的 MXCSR 寄存器不同。切换 x87 和 SSE 状态需要 `fnclex` 和 `stmxcsr`。

ea-FRDT 中的 x87 不是硬件 x87，而是纯软件整数仿真。它把 80 位拆成符号位、15 位指数、64 位尾数，在普通 64 位整数寄存器里做移位、掩码、加法。这意味着它不依赖 CPU 是否真的有 x87 单元——在一个没有 FPU 的嵌入式 ARM 上也能跑 x87 仿真，只是慢。

关键边界：x87 的 80 位格式从 1.0 乘 1.02 到溢出要走 573521 步。这个数字在硬件 x87 和软件仿真上应该一致，因为格式是确定性的。但速度不同——硬件 x87 可能每秒几百万步，软件仿真可能每秒几万步。

## 三、SSE/SSE2：向量浮点的起点

1999 年的 Pentium III 引入 SSE（Streaming SIMD Extensions），8 个 128 位寄存器，每个能装 4 个 float。2001 年的 SSE2 加了 double 支持（每个 128 位寄存器装 2 个 double）。

SSE2 是现代 x86 浮点的事实标准。从 AMD64（x86-64）开始，SSE2 是必须的——64 位模式下不能再用 x87 做主浮点运算，编译器默认用 SSE2。

SSE 的性能边界：

- **128 位宽**：一次 4 个 float 或 2 个 double。比 x87 快 2-4 倍。
- **寄存器堆**：SSE 寄存器是平面的（不是堆栈），编译器可以自由分配，比 x87 好调度。
- **标量指令**：`addss`（scalar single）一次只加一个 float，利用率最低。`addps`（packed single）一次加 4 个，利用率最高。
- **延迟和吞吐**：在 Haswell 上，`addps` 的延迟是 3 个周期，吞吐是每周期 1 条。这意味着你需要 3 个独立的加法链才能填满流水线。

ea-FRDT 的原生 FP32/FP64 路径用的是 C++ `float`/`double`，编译器自动选择 SSE2 标量指令。因为 ea-FRDT 是走路工具，一次只算一个数，不是矩阵乘法，所以向量宽度用不上。这就是为什么一个 i7-6700 跑 FP32 走路每秒几百万步，而不是理论峰值的几十亿步——瓶颈在单步依赖链，不是指令吞吐。

## 四、AVX/AVX2：256 位和 FMA

2011 年 Sandy Bridge 引入 AVX（Advanced Vector Extensions），256 位寄存器（YMM），每个装 8 个 float 或 4 个 double。2013 年 Haswell 加了 AVX2 和 FMA（Fused Multiply-Add，融合乘加）。

AVX2 的性能边界：

- **256 位宽**：比 SSE 翻倍。8 个 float 一次算。
- **FMA**：`vfmadd213ps` 一次做 a×b+c，只有一次舍入，不是两次。这改变了精度——FMA 的中间结果不舍入，比先乘后加更精确。
- **吞吐翻倍**：Haswell 上 FMA 单元每周期能做一条 256 位 FMA，浮点峰值翻倍。
- **降频**：AVX2 重指令会触发 CPU 降频。Intel 的 Turbo Boost 在 AVX2 heavy workload 下会降 200-400MHz。这就是为什么跑 LINPACK 时 CPU 频率反而比跑 SSE 低。

ea-FRDT 的自写格式（FP4/FP6/FP8/BF16/TF32）全部在整数寄存器里仿真，不用 FPU。这意味着 AVX2 对它们没有加速——它们不跑 `vaddps`，它们跑 `add`/`shl`/`and` 这些整数指令。AVX2 能加速的只有原生 FP32/FP64 路径，但那也是标量走路，向量宽度用不上。

## 五、AVX-512：512 位的野心和现实

2016 年 Skylake-X 引入 AVX-512，512 位寄存器（ZMM），每个装 16 个 float 或 8 个 double。

AVX-512 的性能边界：

- **512 位宽**：一次 16 个 float。理论峰值是 SSE 的 4 倍。
- **掩码寄存器**：opmask 寄存器支持按元素掩码，不用写回合并。
- **降频更狠**：AVX-512 heavy workload 会降 400-600MHz。Intel 甚至分了 AVX-512 light 和 heavy 两个档，light 档降频少。
- **双 FMA 单元**：Xeon Scalable 有两个 512 位 FMA 单元，但消费级 i7/i9 通常只有一个。
- **实际收益存疑**：对很多真实负载，AVX-512 的实际加速只有 1.5-2 倍，不是 4 倍。因为降频、内存带宽、非完美循环展开。

ea-FRDT 不直接用 AVX-512。它是单步走路工具，每次一个数，不需要 16 路并行。AVX-512 的价值在于矩阵乘法和卷积，不在于走路。

## 六、ARM NEON 和 SVE：另一边的世界

ARM 的浮点路径和 x86 不同。NEON（Advanced SIMD）是 ARM 的 128 位 SIMD，从 Cortex-A8 开始支持。SVE（Scalable Vector Extension）从 A64FX（富士通的 Fugaku 超算 CPU）开始，向量长度可扩展（128 到 2048 位）。

ARM 的性能边界：

- **NEON 128 位**：和 SSE2 类似，8 个 16 位或 4 个 32 位。
- **没有 x87 遗产**：ARM 原生就是 IEEE 754，没有 80 位扩展精度。没有 binary128 硬件。
- **SVE 可扩展向量**：同一套代码在 128 位和 2048 位机器上都能跑，编译器自动展开。Fugaku 用 512 位 SVE。
- **大小端可选**：ARM 默认小端但可以配大端，x87/x86 是小端。

ea-FRDT 在 ARM 上编译时，原生 float/double 走 NEON 标量指令，自写格式走整数指令。没有 x87/AVX 特有指令，所以 ARM 上行为一致，只是速度不同。

## 七、二进制128 和十进制浮点：硬件缺席

IEEE 754-2008 加了 binary128（112 位尾数）和 decimal128，但几乎没有硬件实现：

- **binary128**：只有 IBM PowerPC 的 VSX 有硬件 support，x86/ARM 都没有。编译器用 `__float128`（libquadmath）软件仿真。ea-FRDT 不用 libquadmath，自己写了纯软件 224 位整数乘法。
- **decimal128**：只有 IBM POWER 和 z/Architecture 有硬件十进制 FPU。x86 没有。GCC 的 `__decimal128` 是软件仿真。ea-FRDT 的 Dec128 用自写 UInt256 大整数乘法。
- **DPD**：IEEE 754 十进制编码，没有硬件解码。全软件查表。

这些格式的性能边界：纯软件，每秒几万到几十万步，不是几百万。Dec128 从 1.0 乘 1.02 到溢出要 714521 步，在纯软件上可能要跑几秒到几分钟。

## 八、缓存和内存边界

指令集不是唯一的边界。缓存层级决定了数据多快能到执行单元：

- **L1 缓存**：32KB，4 周期延迟。ea-FRDT 的工作集（一个浮点数 + 几个整数）完全在 L1 里，没有 cache miss。
- **L2 缓存**：256KB-1MB，12 周期。ea-FRDT 用不到。
- **L3 缓存**：共享，10MB+，40 周期。ea-FRDT 用不到。
- **内存带宽**：ea-FRDT 是标量走路，不搬大块数据，内存带宽不是瓶颈。

这就是为什么 ea-FRDT 在不同 CPU 上的步数一致——它的工作集太小了，缓存在哪一层都不影响。影响速度的是单步算术的延迟，不是吞吐。

## 九、并发和核心边界

ea-FRDT 的 `-m all` 模式把 worker 绑到核心。这里的边界是：

- **核心数**：i7-6700 是 4 核 8 线程。绑 8 个 worker 时两个线程共享一个核心的执行单元，每个 worker 速度降一半。
- **超线程**：超线程不是真核心。两个超线程共享 FPU、ALU、缓存。跑浮点时超线程几乎没有加速。
- **NUMA**：多路服务器上，跨 NUMA 节点的内存访问慢 3 倍。ea-FRDT 不跨节点，每个 worker 在自己的核心上跑自己的状态。
- **频率**：多核满载时 CPU 会降频。i7-6700 单核 Turbo 3.9GHz，8 线程满载可能降到 3.4GHz。

## 十、总结：指令集和走路工具的关系

对一个走路工具来说，指令集的作用不是"加速"——因为它一次只算一个数，不需要向量宽度。指令集的作用是：

1. **决定哪些格式能原生跑**：FP32/FP64 在所有 CPU 上都有硬件；FP128/Dec128 在任何 CPU 上都没有硬件，全靠软件。
2. **决定软件仿真的速度**：整数乘法在 64 位寄存器上比 32 位快一倍；有 `mulx`（BMI2）的 CPU 做 64 位乘法不带 flags，更快。
3. **不决定步数**：步数是格式的数学性质，和 CPU 无关。FP32 从 1.0 乘 1.02 到溢出永远是 4481 步，不管你用 i7-6700 还是 Fugaku。

ea-FRDT 的价值在于：它不依赖任何特定指令集。它能在一个没有 FPU、没有 AVX、没有 NEON 的 CPU 上跑完全套 17 种格式。慢，但正确。这就是纯软件仿真的意义——不是为了快，是为了可移植和可审计。

算法本身可能会开小差。
