# 为什么 ea-FRDT 是"四不像"

## 一、先把"四不像"说清楚

市面上和"浮点 + 硬件 + 性能"沾边的工具，按用户使用场景切成五个类目：烤机/压力测试、浮点基准、教学可视化、编译器/数值库测试、十进制浮点编解码库。ea-FRDT 每一个类目都沾边，但每一个类目都不完全是。

| 类目 | 典型代表 | 它干什么 | 它不干什么 |
|---|---|---|---|
| 烤机 / 压力测试 | Prime95、OCCT、AIDA64 Stress、Cinebench | 把 CPU/GPU 跑高温，验证稳定性 | 不关心 bit-exact，不输出每一步的值，不做浮点格式参考 |
| 浮点基准 | STREAM、LINPACK、CoreMark、Dhrystone | 测 GFLOPS / 带宽 / MIPS，给排行榜打分 | 不做长程遍历，不关心边界值，结果可以被编译器优化掉 |
| 教学 / 可视化 | phet float playground、float.stefan.com.br | 浏览器里输入一个数看它的位表示 | 不榨硬件，不做压力，不做十进制浮点，不做长程遍历 |
| 编译器 / 数值库测试 | boost.math、libFuzzer、glibc math testsuite、llvm test-suite | 测数学函数正确性，找编译器 bug | 不做硬件压力，不做边界遍历，不输出 bit 流，不做性能压榨 |
| 格式转换 / 编解码 | libdecnumber、mpdecimal、Intel RDFP | 十进制浮点格式转换、算术 | 不做压力，不做遍历，不做硬件优先级，不做 dump 流 |

ea-FRDT 同时具备五者的一部分：
- 烤机工具的**硬件压力**（绑核、实时优先级、0ms delay、ALU 满载）
- 基准测试的**可复现步数**（17 格式溢出步数基线固定）
- 教学工具的**位级参考**（`--bits bin/hex` 每步输出位模式）
- 编译器测试的**确定性**（同起点同参数永远输出同一步序列）
- 编解码库的**完整格式覆盖**（17 种浮点格式从 fp4 到 fp128，BID 和 DPD 两套十进制编码）

但它在任何一个类目里都"不称职"：
- 烤机用户要 GUI、温度曲线、厂商认证——没有
- 基准用户要 GFLOPS 排行榜、跨平台对比——没有，我们是反基准
- 教学用户要浏览器、交互式——没有，纯 CLI
- 编译器测试要单元测试框架、覆盖率报告——没有，只有一个 CLI 和一个 `--self-test`
- 编解码库要可链接的 `.a` / `.so` / C ABI——只有一个轻量 `c_api.h`，不是主目标

这就是"四不像"：每类用户都觉得它"有点像但不够像"，没有一类用户是它的主场。

## 二、为什么不做烤机工具

烤机工具的商业模式决定了它必须**讨好厂商**：

- Prime95 的 Small FFT 故意不压到边界，因为压太狠会让用户的 CPU 报 WHEA 错误然后来找作者售后。
- OCCT 有"自定义错误容忍度"，因为真跑到硬件边界就会蓝屏，作者不想被寄律师函。
- AIDA64 收硬件厂商赞助，不能真把 CPU 推到不稳定区间，否则厂商下次不给钱。
- Cinebench 是营销工具，分数好看比 bit-exact 重要。

它们的"遮羞布"：
- 用 SIMD 峰值包装分数，但实际 ALU 利用不满
- 超线程一开分就涨，因为压力落在了共享执行单元上而不是独占核
- 温度一高就降频，但报告里只报峰值不报均值
- 错误检测是采样式，不是每步检查
- 故意留一点余量，让用户烤一小时也不会触发硬件保护

ea-FRDT 不做这些。我们：
- 绑核独占（`--pin`），不超线程占便宜——超线程对我们工具的每核提升只有 1.1-1.3×，因为我们榨的是标量 ALU，不是 SIMD 管道
- 0ms delay，不主动让 CPU 休息
- 每步都是精确的浮点乘法，编译器不能把它优化掉（因为结果要输出、要 dump、要写文件）
- 不报告温度，不报告频率，不报告 GFLOPS——只报步数
- 不讨好任何人，谁赞助都不改行为
- 实时优先级 + best-effort SCHED_BATCH（Linux），把调度器延迟压到最小

这意味着烤机用户会觉得我们"不专业"——没有温度曲线、没有错误检测、没有界面、没有压力测试预设。但我们的目标根本不是烤机用户。烤机用户要的是"我这颗 CPU 稳不稳"，我们要的是"从 1.0 走到 inf 一共多少步、每步 hex 是什么"。这两个问题完全正交。

## 三、为什么不做基准测试

基准测试的目的是**排名**。排名需要：
- 标准化的工作负载（LINPACK 的矩阵大小固定，CoreMark 的迭代数固定）
- 跨平台可比（同一程序跑在不同 CPU 上，数字有意义）
- 可以被优化（编译器越狠分越高，厂商专门调优）
- 有"好"和"坏"的客观标准（分数高就是好 CPU）

ea-FRDT 反着来：
- 工作负载是"从 1.0 走到 inf 的浮点步数"，这个数只和 IEEE 754 格式有关，和 CPU 性能**几乎无关**——步数固定，不随 CPU 变
- 跨平台步数必须完全一致（这是特性，不是 bug）——所以不能优化
- 没有 GFLOPS，只有"多少秒跑完 fp32 的 4481 步"——这个秒数受温度、调度、DVFS、前台后台影响，不可排名
- 不输出分数，只输出 step 序列和退出原因
- 故意不做 SIMD，因为 SIMD 会让不同架构数字不可比

这意味着基准测试用户会觉得我们"没数字可比"。但我们的目标不是比 CPU 谁快，是验证**同一个浮点序列在不同硬件上是否 bit-exact**。如果你改了编译器、改了 libc、改了内核调度策略，跑一遍 ea-FRDT，步数变了，就说明你改坏了。这是反基准：基准测快不快，我们测对不对。

## 四、为什么不做教学工具

教学工具要可视化、要交互式、要在浏览器里跑、要 0 安装。我们是一个 ≈680 KB 的 CLI，Windows 下要装 MSYS2，没有 GUI，没有网页。

教学用户要的是"输入 0.1+0.2 看为什么不等于 0.3"。我们要的是"从 0.1 出发每步乘 1.02，走到 overflow 一共多少步，每一步的 hex 是什么，BID 和 DPD 编码在这个值上差几位"。完全不是一个需求。

我们的文档里有位表、有 BID combo5 联合编码推导、有 UInt256 schoolbook 乘法分析——这些内容比任何在线教学都硬核，但它们是写给**已经会 IEEE 754 的人**看的参考资料，不是写给初学者的入门教程。初学者不会读这种文档，我们也不打算吸引初学者。

## 五、为什么不做编译器测试

编译器测试（boost.math / libFuzzer / glibc math testsuite / llvm test-suite）要：单元测试框架、覆盖率报告、CI 集成、固定的输入语料库、和被测编译器一起发布。

我们是一个独立的 CLI 二进制，没有单元测试框架（只有一个 `--self-test` 子命令做纯逻辑自检），没有覆盖率，不挂进任何第三方 CI，不随编译器发布。

但我们的**副产品**是编译器测试：如果你改了 glibc 的 decimal128 软件实现，跑一遍 ea-FRDT，dec128 的步数从 714521 变成别的数，就说明你改坏了。如果你改了 clang 的 x87 codegen，x87 的步数变了，就说明 codegen 有 bug。这是被动价值，不是主动定位。我们不打算接进 llvm test-suite，不打算写 CMake 的 CTest，因为那会把我们绑死在编译器测试这个类目里，失去四不像的自由度。

## 六、为什么不做编解码库

libdecnumber / mpdecimal / Intel RDFP 是给程序链接用的库：你 `#include <decfloat.h>`，调用 `decimal32_add()`，拿到结果。它们：
- 不做压力，不绑核，不调实时优先级
- 不做遍历，不做"从 1.0 走到 inf"
- 不输出 bit 流，不做 dump
- 不做 17 格式统一抽象
- 不做并发 worker 池

我们有一个 `libeafrdt/` 目录带 `c_api.h`，但那是副产品，不是主目标。主目标是 CLI 行走器。别人要链接我们的库，可以，但我们不为库的 ABI 兼容性负责，不做 semver，不做稳定 API。这又把我们和正式的十进制浮点库区分开了。

## 七、四不像定位带来的具体优势

### 7.1 搜索缝隙里没有竞争者

Google 搜"prime95 decimal128"——没有结果。
搜"fp128 overflow step count"——没有结果。
搜"BID DPD schoolbook 256-bit multiplier"——我们自己。
搜"x87 80-bit vs fp128 step comparison"——我们自己。
搜"bit-exact float walker stress CPU"——我们自己。
搜"dpd128 pack unpack self check"——没有第二个开源实现。

这些词单独看每个都是冷门，但组合起来就是一个**完全没人占的生态位**。别人要做这个产品，得同时：
- 真的懂 IEEE 754 全部格式（包括 BID/DPD 十进制、x87、fp128、fp8）
- 愿意用纯软件写 17 个格式的引擎
- 愿意拒绝 MSVC
- 愿意做一个 ≈680 KB CLI 而不是 GUI
- 愿意不做排行榜不做营销
- 愿意写 4000-8000 字的技术文档而不是 README 一页

这六个条件是 AND，不是 OR。少一个就填不上。

### 7.2 来的用户是"自带需求"的

普通工具的用户是被营销拉来的——他们本来不知道自己需要这个，看了广告才觉得"也许有用"。这些用户提的 issue 是"能不能加个 GUI"、"能不能支持 MSVC"、"能不能加个云同步"。

四不像的用户是**自己带着问题来的**：
- 他正在写一个 decimal128 编译器运行时，需要对照参考实现
- 他正在测一个新 CPU 的 ALU，需要一个能确定性跑满标量管道的负载
- 他正在写 IEEE 754 论文，需要一个 bit-exact 的步数基线表
- 他正在调一个 x87 软件模拟，需要对照 x87 的真实 overflow 点
- 他正在审计金融系统的十进制浮点舍入，需要一个参考步序列

这些人不需要被说服"你需要这个工具"。他们打开 GitHub，搜一个非常具体的问题，找到我们，clone，跑，然后要么不提 issue（直接用），要么提一个极高质量的 issue（"你们在 ARM64 上 `bit_length()` 的 `__builtin_clzll` 返回值不对"、"DPD128 在 subnormal 边界的 pack 漏了一个 declet"）。

### 7.3 没有对标，就没有无意义讨论

L 型仓库最累的事情之一是：评论区永远有人问"这和 Rust 的 xxx 库比怎么样"、"这和 Python 的 decimal 模块比"、"这和 Intel 的 RDFP 比"。这些问题回答不完，因为我们不是这些东西的任何一个。

四不像定位让这种问题自动消失——因为没有对标。我们不做库，不做教学，不做烤机，不做基准。你要对比，得自己先想清楚你要对比什么维度。这种"无对标"状态是一种保护：它让项目不被外部期望绑架，不用跟着别人的路线图走。

### 7.4 长期价值不随技术栈过期

Prime95 会过时，因为 AVX-512 普及后 Small FFT 工作负载就变了。Cinebench 会过时，因为新架构新指令集需要新分数。STREAM 会过时，因为内存带宽标准在变。SPEC CPU 会过时，因为它的工作负载被厂商专门调优。

但 IEEE 754 标准不会变。fp32 从 1.0 走到 inf 是 4481 步——这个数字在 1985 年 IEEE 754 发布时就是 4481，2085 年还是 4481。BID dec128 的系数是 110 位——这个标准字段不会改。x87 是 80 位——这个规格从 1980 年代就定了。DPD 的 3 位十进制数字编码成 10 位 bit 的 declet 结构，是 IEEE 754-2008 的标准附录，不会改。

我们的步数基线表是一个**数学事实**，不是一个工程优化。数学事实不会过期。五年后有人写新的浮点硬件，他还需要对照这个步数表。十年后有人研究 IEEE 754 十进制编码，他还需要这个 BID/DPD 对照。这就是 J 型长尾的物理基础——我们的资产不是代码，是那 17 个固定的步数数字和它们对应的位模式。

## 八、四不像定位的代价

### 8.1 不铺渠道的真实原因：成本与账号

不主动铺渠道，直接原因不是"内容没人收"，而是**运营成本与账号门槛**：每个渠道都要注册、实名、养号、持续发帖维护、回复评论，遇到限流或封号还得重来；这些都是时间与金钱投入，项目不承担。内容与类目不匹配只是第二层原因——即便内容匹配，也没有预算和账号去运营。

以下只是"即便投入也难精准"的观察，不构成"无法传播"的绝对判断：

V2EX 有"分享创造"节点，但我们是什么类？C++？硬件？开源？都不完全是。发出去会被回复"这是个啥？烤机？教学？"，解释成本极高。

Reddit 的 r/programming、r/cpp、r/hardware 都不是精准目的地。r/programming 要宏观话题，r/cpp 要语言特性，r/hardware 要硬件测评。我们是三个的交叉点，三个都不收。Hacker News 更不会收——它要的是"颠覆世界"的产品，不是一个 ≈680 KB 的 CLI。

### 8.2 文档必须自己写全

普通工具的用户会自己去 Stack Overflow 问。但四不像的用户搜不到 Stack Overflow——因为我们做的事情 Stack Overflow 上没人问过。"BID combo5 联合编码的前导十进制位怎么提取"、"DPD declet 串联时进位怎么传"、"UInt256 schoolbook 乘法双循环的双进位检测"——这些问题搜不到任何答案。

所以 README、docs/、BASELINE、IMPLEMENTATION、UINT256、COMPLEXITY 文档全部要自己写到 4000-8000 字，把用户可能问的问题全预先回答了。这就是为什么我们的文档比代码还长。这不是风格，是定位决定的——没有社区帮我们回答问题。

### 8.3 无法招到普通贡献者

普通开源项目招贡献者的路径：good first issue → 修 bug → 加 feature。我们没有 good first issue，因为代码全是位级浮点算法，一个新来的人连 BID combo5 编码表都要先读一周。他得先懂 IEEE 754 十进制、懂 schoolbook 大整数、懂 C++23、懂 MSYS2，然后才能在我们代码里改一个数字。

这意味着项目长期是单人维护。这是我们接受的代价——单人维护的好处是路线不漂移，不会被 PR 拉去做 GUI、做 GPU、做 MSVC、做 WebAssembly、做 Python binding。这些"正常人想要"的功能，我们一个都不做。

### 8.4 流量曲线是 J 型，不是 L 型

L 型仓库公开后 72 小时流量冲顶，然后衰减。J 型仓库公开后 3-6 个月几乎零流量，然后缓慢爬升。其中前 3-5 个月是**结构性黑暗期**，原因不在内容：搜索引擎先要发现仓库（爬虫抓取、sitemap 收录），再建索引，再让排名稳定，这一套本身就要数月；新仓库没有外链和 star 积累，权重还得更久才起来。所以"已经能被搜到"和"能被人搜到"之间隔着几个月，这段黑暗期是确定项，不是运气问题。我们选的就是 J 型——主动挑稀缺标签、写长 README、起炸裂仓库名、不推广社区。代价就是前几个月看着 GitHub Insights 里的 Unique cloners 个位数，怀疑是不是没人看。

## 九、这个缝隙会不会被填上

理论上会。但实际上很难，因为填这个缝隙需要同时满足：
- 作者真的懂 IEEE 754 全部格式（包括 BID/DPD）
- 作者真的愿意写 17 个格式的纯软件引擎
- 作者真的愿意拒绝 MSVC、拒绝 GUI、拒绝排行榜
- 作者真的愿意做一个 ≈680 KB CLI 而不是 Web 应用
- 作者真的愿意花半年写文档而不是写营销文案
- 作者真的愿意单人维护、不接 PR 拉路线

这六个条件是 AND，不是 OR。少一个就填不上。

市面上所有"看起来像"的项目，都至少缺两个：
- mpdecimal 是库，不是压力工具
- Prime95 是压力工具，不做十进制浮点
- boost.math 是数学库，不做硬件优先级
- float playground 是教学，不做遍历
- llvm test-suite 是测试框架，不是独立 CLI
- Intel RDFP 是厂商参考库，不做 BID/DPD 双路径

我们占的这个缝，短期（1-2 年）不会有人来抢。长期（5 年+）可能会有人 fork 或模仿，但那时候我们已经是 Google 搜索结果第一，后来者只能跟在后面。

## 十、一句话总结

我们不做任何主流类目的第一名，做主流类目之间那个无人缝隙的唯一一名。这个缝隙之所以空着，不是因为没人想到，是因为同时满足那六个 AND 条件的人本来就少。这就是"四不像"的全部意义。
