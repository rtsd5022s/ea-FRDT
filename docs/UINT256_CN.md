# UInt256 技术原理

## 为什么需要这个东西

dec128 的系数是 110 位二进制整数（IEEE 754-2008 BID 布局）。从 `1.0` 出发每步乘 `1.02`，等价于系数乘以 `102`、指数减 `2`，然后规范化。问题在于：两个 110 位整数相乘，中间结果是 220 位。C++ 标准里最大的无符号整数是 `uint64_t`，连 128 位都没有；编译器扩展 `__int128` 在 GCC/Clang 里有，MSVC 里没有，而且它只能装 128 位，220 位还是装不下。

所以必须自己造一个大整数。这个项目选了最小可用集合：**UInt256**，四个 `uint64_t` 字，总共 256 位。256 位够装 110×110=220 位的乘积，还留 36 位余量给进位。接口刻意做得极薄：只有乘法、除以 10、比较、取低位。加法、减法、移位、序列化都没写——因为 dec128 行走器用不到，少写少错。

这个头文件被标记为实验性，编译时可以走 `-O0`（不优化）来对照优化开关对大整数乘法的影响。正式构建用 `-O2`，编译器会把 `mul64` 里的 32 位乘法自动折叠成硬件的 `mul` 指令，配合 ADX 扩展的 `mulx` 拿到两个 64 位结果。

## 数据结构

```cpp
struct UInt256 {
    std::uint64_t w[4] = {0,0,0,0};
};
```

四个字，`w[0]` 是最低位（least significant），`w[3]` 是最高位。这种小端字序（little-endian word order）是大整数算法的标准选择：进位从 `w[0]` 向 `w[3]` 传播，索引递增方向就是进位传播方向，写循环时不容易搞反。

构造函数只接受一个 `uint64_t`，相当于把它塞进 `w[0]`，高三个字清零。没有从字符串构造、没有从 `double` 构造——那些都在上层做，UInt256 本身只认整数。

## mul64：64×64 怎么拆成 32×32

最底层的运算是 `mul64(x, y, lo, hi)`：输入两个 64 位无符号整数，输出 128 位乘积的低 64 位和高 64 位。

最直接的写法是用编译器扩展：

```cpp
unsigned __int128 r = (unsigned __int128)x * y;
lo = (uint64_t)r;
hi = (uint64_t)(r >> 64);
```

但这个项目不用 `__int128`，原因有三：第一，可移植性——万一以后要在不支持 `__int128` 的工具链上编译，这个头文件不能崩；第二，教学目的——拆成 32 位乘法能看清楚 128 位乘积到底怎么来的；第三，在 64 位 x86 上，编译器看到 32 位乘法链会自己识别成 `mulx`，生成的机器码和手写 `__int128` 几乎一样。

拆法是标准的 Schoolbook 乘法：

```
x = x1 * 2^32 + x0
y = y1 * 2^32 + y0
x*y = x1*y1 * 2^64 + (x1*y0 + x0*y1) * 2^32 + x0*y0
```

四个 32×32 乘积：

```cpp
uint64_t p0 = x0 * y0;   // 低 64 位
uint64_t p1 = x0 * y1;   // 中低
uint64_t p2 = x1 * y0;   // 中高
uint64_t p3 = x1 * y1;   // 高 64 位
```

关键是中间段怎么拼。`p0` 的高 32 位、`p1` 的低 32 位、`p2` 的低 32 位加在一起，形成中间项：

```cpp
uint64_t mid = (p0 >> 32) + (p1 & 0xFFFFFFFF) + (p2 & 0xFFFFFFFF);
```

这里 `mid` 最多是三个 33 位数相加，约 35 位，不会溢出 64 位。然后：

```cpp
lo = (p0 & 0xFFFFFFFF) | (mid << 32);
hi = p3 + (p1 >> 32) + (p2 >> 32) + (mid >> 32);
```

`lo` 的低 32 位是 `p0` 的低 32 位，高 32 位是 `mid` 的低 32 位。`hi` 是 `p3` 加上 `p1`/`p2` 的高 32 位，再加上 `mid` 溢出到高位的部分。整个过程没有分支，没有循环，固定 6 条算术指令。

在 x86-64 上，GCC/Clang 看到这段代码会把它折叠成一条 `mulx r8, r9, r10`（ADX 扩展）或者 `mul r/m64`（经典 MUL），硬件一次算出 128 位乘积。也就是说，源码写的是"软件模拟 128 位乘法"，机器跑的是硬件乘法器。

## mul128：128×128 怎么拼成 256 位

`mul128(a_lo, a_hi, b_lo, b_hi)` 是两个 128 位数相乘，输出 256 位。这里把 128 位数表示成两个 64 位字：`a = a_hi * 2^64 + a_lo`，`b = b_hi * 2^64 + b_lo`。

展开：

```
a*b = a_hi*b_hi * 2^192
    + (a_hi*b_lo + a_lo*b_hi) * 2^64
    + a_lo*b_lo
```

三次 `mul64` 调用：

1. `mul64(a_lo, b_lo, r.w[0], r.w[1])`——最低两项乘积，直接填 `w[0]` 和 `w[1]`。
2. `mul64(a_hi, b_lo, lo, hi)`——第二项的左半，加到 `w[1]`，进位到 `w[2]`。
3. `mul64(a_lo, b_hi, lo, hi)`——第二项的右半，加到 `w[1]`，进位到 `w[2]` 和 `w[3]`。
4. `mul64(a_hi, b_hi, lo, hi)`——最高项，加到 `w[2]`，进位到 `w[3]`。

进位检测是这段代码最容易写错的地方。两个 64 位数相加 `c = a + b`，如果溢出，`c` 会小于 `a`（无符号回绕）：

```cpp
uint64_t c = r.w[1] + lo;
uint64_t carry1 = (c < r.w[1]) ? 1ULL : 0ULL;
r.w[1] = c;
```

这个 `c < r.w[1]` 就是进位标志。它等价于 x86 的 `add` 指令自动设置的 CF 位，但在 C++ 里不能直接读 CF，只能用这种无符号回绕检测。编译器会把它识别成条件传送（cmov），不会真的分支。

第二段更复杂，因为要加三个东西：

```cpp
uint64_t c2 = r.w[2] + hi + carry1;
r.w[2] = c2;
r.w[3] = (c2 < r.w[2] + carry1) ? 1ULL : 0ULL;
```

这里 `r.w[2] + carry1` 是中间值，`c2` 如果比它小，说明 `hi` 加进去又溢出了，再进位到 `w[3]`。

最后一项：

```cpp
c = r.w[2] + lo;
uint64_t carry2 = (c < r.w[2]) ? 1ULL : 0ULL;
r.w[2] = c;
r.w[3] += hi + carry2;
```

整个 `mul128` 调用四次 `mul64`，每次 6 条指令，加上进位传播的加法，总共大约 30 条算术指令。对 256 位乘法来说，这是 Schoolbook 的理论最小值（n=4 字，n²=16 次 64 位乘法，但因为 `mul64` 内部拆 32 位，实际是 16 次 32×32）。

## div10：除以 10 取余

dec128 行走器每步乘完 `102` 后，要把系数规范化：如果系数超过 10^33-1，就除以 10、指数加 1，直到系数回到合法范围。这个除法不是通用除法——除数固定是 10，余数要保留（余数就是被舍掉的最后一位十进制数字，用于舍入判断）。

算法从最高字 `w[3]` 到最低字 `w[0]` 逐字处理。关键常数：

```
2^64 / 10 = 0x1999999999999999
2^64 % 10 = 6
```

这个常数怎么来的？因为 `2^64 = 10 * 0x1999999999999999 + 6`。当高一位已经算出余数 `rem` 时，当前字 `w[i]` 实际代表的数是 `rem * 2^64 + w[i]`。除以 10：

```cpp
uint64_t q = w[i] / 10;
uint64_t r = w[i] % 10;
q += rem * 0x1999999999999999ULL;
r += rem * 6ULL;
q += r / 10;
r = r % 10;
w[i] = q;
rem = r;
```

`w[i] / 10` 是当前字本身除以 10 的商，`rem * 0x1999...` 是高位余数带来的商增量。余数部分先 `r += rem * 6`，再 `r /= 10` 把它折成商，`r %= 10` 留下新余数。

这个技巧叫"多精度除以单精度"（short division），和手工竖式除法一模一样：从高位到低位，每次带着上一位的余数除当前位。除数 10 是常数，编译器会把 `w[i] / 10` 和 `w[i] % 10` 优化成乘法+移位（不真的调用除法指令），所以很快。

返回值是最终余数，也就是整个 256 位数除以 10 的余数。这个余数在 dec128 舍入里决定最后一位十进制数字是 0 到 9 中的哪个，进而决定就近舍入时该进还是该舍。

## ge 和 to_lo：两个工具函数

`ge(v)` 是判断 `this >= v`（v 是一个 64 位数）。逻辑：

```cpp
if (w[3] || w[2] || w[1]) return true;
return w[0] >= v;
```

高三个字任何一个非零，说明这个数至少是 2^64，必然大于 64 位数 `v`。否则只看 `w[0]`。这个函数在 dec128 规范化循环里用：只要系数还大于等于 10^33，就继续除以 10。

`to_lo()` 直接返回 `w[0]`。规范化结束后，系数应该已经缩回 110 位以内，低 64 位就是实际的系数低位，直接取出来打包成 BID 位串。

## 为什么不用 Karatsuba 或 FFT

256 位乘法如果用 Karatsuba，可以把 4 次 `mul64` 降到 3 次（递归展开）。但 256 位太小了：Karatsuba 的递归开销（额外的加法、减法、临时变量）在 n=4 时反而比 Schoolbook 慢。n 到 16 字以上 Karatsuba 才开始划算，n 到 100 字以上 Toom-Cook 才值得考虑，FFT（Schönhage-Strassen）要到几千位才有用。

这个项目的 256 位乘法每步只跑一次，整个 dec128 行走器跑 71 万步，总乘法次数 71 万。每次乘法 30 条指令，总共 2130 万条指令，在 i7-6700 上大约 2.6 秒。如果换成 Karatsuba，每次乘法可能省 5 条指令，总共省 350 万条，大约省 0.4 秒——但代码复杂度翻倍，调试时间远超 0.4 秒。不划算。

## 为什么不写加法和移位

一个完整的大整数库应该有加法、减法、左移、右移、比较、序列化、字符串转换。这个 UInt256 一样都没有。原因是：

- **加法**：dec128 行走器不需要。乘 1.02 是乘法+除法，不是加法。
- **减法**：同上。
- **移位**：`mul64` 内部已经用 `>> 32` 和 `<< 32` 做了显式移位，不需要通用移位函数。
- **序列化**：BID 打包在上层做，UInt256 只负责算。

少写一个函数就少一个 bug 源。这个项目的哲学是"按需实现"，不是"写一个通用大整数库"。如果以后要支持其他十进制操作（比如 dec64 的加法），再补加法函数。

## 性能特征

在 i7-6700（Skylake，支持 ADX）上，`mul64` 编译后大约是：

- 2 条 `mov` 拆高低 32 位
- 4 条 32×32->64 `imul`
- 3 条加法拼中间项
- 2 条位运算拼 lo/hi

总共约 11 条指令，延迟 3 个周期，吞吐量每周期 1 条（因为 `imul` 是流水线的）。

`mul128` 调 4 次 `mul64`，加上进位传播，大约 40 条指令，延迟约 15 个周期。71 万次乘法串行执行，总延迟 1065 万周期，在 3.4 GHz 上是 3.1 秒——和实测的 2.6 秒基本吻合（超标量和缓存命中会再压一点）。

如果编译时用 `-O0`，编译器不会折叠 32 位乘法链，会真的生成 32 位 `imul` 指令序列，速度大约慢 3-5 倍。这就是为什么这个头文件在正式构建里走 `-O2`，只有实验对照时才 `-O0`。

## 和 BID/DPD 的关系

UInt256 只服务于 BID 路线的 dec128。DPD 路线不用大整数——DPD 把系数存成 `std::vector<int>` 十进制数字数组，逐位乘法+进位，不需要二进制大整数。两条路线是独立的：BID 走二进制整数乘法（快但要大整数），DPD 走十进制数组乘法（慢但不用大整数）。

实测下来，DPD128 比 BID Dec128 还快，因为 UInt256 的 Schoolbook 乘法虽然用了硬件乘法器，但每次乘法的延迟还是比 DPD 的逐位十进制乘法（查表+一位加法）高。这反过来印证了：在 110 位这个量级，大整数乘法不一定比十进制数组快。

## 局限性

- **没有符号位**：纯无符号。dec128 的符号存在 BID 位串的最高位，不放在 UInt256 里。
- **没有溢出检测**：`mul128` 假设乘积不会超过 256 位。对 110×110=220 位来说够，但如果上层传错参数传了满 128 位，乘积会溢出 `w[3]`。
- **没有赋值运算符**：用默认拷贝构造。四个 64 位拷贝很便宜。
- **没有打印函数**：调试时要自己写 `printf("%016lx %016lx %016lx %016lx", w[3], w[2], w[1], w[0])`。

这些局限是刻意的。这个头文件是 dec128 行走器的内部零件，不是给外部用的通用库。
