# UInt256 / UInt128 技术原理

## 定位

`include/uint256.h` 与 `include/uint128.h` 是两个**独立 drop-in single-header 库**，只依赖 `<cstdint>`、`<cstring>`、`<string>` 三个标准头，不依赖项目内任何其他头文件。`#include "uint256.h"` 即可在任意 C++23 GCC/Clang 工程里使用，不耦合 ea-FRDT 的浮点引擎。

主程序与 `libeafrdt/` C ABI 静态库共用这一份实现：库里原来自带的 `UInt256` 副本已删除，改为 `#include "../include/uint256.h"` 加 `using fw::UInt256`（保持 `fw::core::UInt256` 的既有拼写），依赖方向单向——库依赖主头文件，主头文件不反向依赖库。

最初它们只是 dec128(BID) 行走器的内部零件——四个 64 位字，只有乘 10、除以 10、比较大小三个函数，因为行走器只用到这三件事。随着 BID 编码层补全（`engine_bid_codec.h` 的 combo5 联合编码需要前导十进制位提取）、dec128 舍入逻辑需要精确的进位链（`dec_round` 在系数末尾进位时要逐级 inc/add_small）、以及独立自测的需要，这个头文件逐步长成了一个完整的小整数库：运算符重载、十进制字符串互转、左移右移、通用小整数除法、位长查询、零检测，全部带 10 项断言的独立 self-test（`tests/tmp/uint_selftest.cpp`）。

`UInt128` 是 `UInt256` 的对称两字版本：`w[2]` 两个 `uint64_t`，服务于 x87 与 FP128 的纯软件尾数中间积辅助（那里 128 位足够装下两个 56 位尾数的乘积），以及 `drive.h` 里的步数计数器（u128）。两者 API 完全对称，只是字长减半。

## 为什么需要大整数

dec128 的系数是 110 位二进制整数（IEEE 754-2008 BID 布局）。从 `1.0` 出发每步乘 `1.02`，等价于系数乘以 `102`、指数减 `2`，然后规范化——如果系数超过 `10^33 - 1`，就反复除以 10、指数加 1，直到系数缩回合法范围。

问题在于：两个 110 位整数相乘，中间结果是 220 位。C++ 标准里最大的无符号整数是 `uint64_t`，连 128 位都没有；编译器扩展 `__int128` 并非所有工具链都提供（MSVC 就没有），而且它只能装 128 位，220 位还是装不下。x87/FP128 的尾数中间积用 `__int128` 辅助是因为只到 128 位；dec128 的 220 位乘积必须自己造大整数。

所以选了 **UInt256**：四个 `uint64_t` 字，共 256 位。256 位够装 110×110=220 位的乘积，还留 36 位余量给进位传播。这个余量不是浪费——Schoolbook 乘法的双重循环里，中间累加可能产生额外进位，多 36 位保证不需要边界检查。

## 数据结构

```cpp
struct UInt256 {
    std::uint64_t w[4] = {0,0,0,0};
};
```

四个字，`w[0]` 是最低位（least significant），`w[3]` 是最高位。这种小端字序（little-endian word order）是大整数算法的标准选择：进位从 `w[0]` 向 `w[3]` 传播，索引递增方向就是进位传播方向，写循环时不容易搞反。如果用大端字序（`w[0]` 最高），进位要从 `w[3]` 往 `w[0]` 传，循环索引要倒着数，每次写乘法加法都要 mind the reversal，bug 率显著上升。

构造函数有三个：`UInt256()` 默认全零；`UInt256(v)` 把一个 64 位数塞进 `w[0]`，高三个字清零；`UInt256(w0,w1,w2,w3)` 四字全给。没有从 `double` 构造、没有从 `long double` 构造——浮点和二进制大整数的转换在上层做，UInt256 本身只认整数。

## mul64：64×64 怎么拆成 32×32

最底层的运算是 `mul64(x, y, lo, hi)`：输入两个 64 位无符号整数，输出 128 位乘积的低 64 位和高 64 位。

最直接的写法是用编译器扩展：

```cpp
unsigned __int128 r = (unsigned __int128)x * y;
lo = (uint64_t)r;
hi = (uint64_t)(r >> 64);
```

但 UInt256 这个头文件不用 `__int128`，原因有三：第一，可移植性——这个头文件是 drop-in，万一以后要在不支持 `__int128` 的工具链上编译（比如某些嵌入式编译器、或者用户排斥 MSVC 但未来可能用别的），这个头文件不能崩；第二，教学目的——拆成 32 位乘法能看清楚 128 位乘积到底怎么来的，调试时能逐位对上；第三，在 64 位 x86 上，编译器看到 32 位乘法链会自己识别成 `mulx`（ADX 扩展）或 `mul`（经典 MUL），生成的机器码和手写 `__int128` 几乎一样。

拆法是标准 Schoolbook 乘法：

```
x = x1 * 2^32 + x0
y = y1 * 2^32 + y0
x*y = x1*y1 * 2^64 + (x1*y0 + x0*y1) * 2^32 + x0*y0
```

四个 32×32 乘积：

```cpp
uint64_t p0 = x0 * y0;   // 低 64 位
uint64_t p1 = x0 * y1;   // 中低
uint64_t p2 = x1 * y0;   // 中高
uint64_t p3 = x1 * y1;   // 高 64 位
```

关键是中间段怎么拼。`p0` 的高 32 位、`p1` 的低 32 位、`p2` 的低 32 位加在一起：

```cpp
uint64_t mid = (p0 >> 32) + (p1 & 0xFFFFFFFF) + (p2 & 0xFFFFFFFF);
```

这里 `mid` 最多是三个 33 位数相加（每个项最大是 2^33-1，因为 p1/p2 是 32×32→64，低 32 位最大 2^32-1，p0 高 32 位也是 2^32-1），约 35 位，不会溢出 64 位。这个"不会溢出"是关键正确性论证：如果中间项可能溢出，整个拼法就错了。

然后：

```cpp
lo = (p0 & 0xFFFFFFFF) | (mid << 32);
hi = p3 + (p1 >> 32) + (p2 >> 32) + (mid >> 32);
```

`lo` 的低 32 位是 `p0` 的低 32 位，高 32 位是 `mid` 的低 32 位。`hi` 是 `p3` 加上 `p1`/`p2` 的高 32 位，再加上 `mid` 溢出到高位的部分。整个过程没有分支，没有循环，固定 6 条算术指令。

在 x86-64 上，GCC/Clang 看到这段代码会把它折叠成一条 `mulx r8, r9, r10`（ADX 扩展，三个操作数不覆盖输入）或者 `mul r/m64`（经典 MUL，结果固定在 rdx:rax），硬件一次算出 128 位乘积。也就是说，源码写的是"软件模拟 128 位乘法"，机器跑的是硬件乘法器，没有性能损失。

## mul128：128×128 怎么拼成 256 位

`mul128(a_lo, a_hi, b_lo, b_hi)` 是两个 128 位数相乘，输出 256 位。这里把 128 位数表示成两个 64 位字：`a = a_hi * 2^64 + a_lo`，`b = b_hi * 2^64 + b_lo`。

展开：

```
a*b = a_hi*b_hi * 2^192
    + (a_hi*b_lo + a_lo*b_hi) * 2^64
    + a_lo*b_lo
```

四次 `mul64` 调用：

1. `mul64(a_lo, b_lo, r.w[0], r.w[1])`——最低两项乘积，直接填 `w[0]` 和 `w[1]`。
2. `mul64(a_hi, b_lo, lo, hi)`——第二项的左半，加到 `w[1]`，进位到 `w[2]`。
3. `mul64(a_lo, b_hi, lo, hi)`——第二项的右半，加到 `w[1]`，进位到 `w[2]` 和 `w[3]`。
4. `mul64(a_hi, b_hi, lo, hi)`——最高项，加到 `w[2]`，进位到 `w[3]`。

进位检测是这段代码最容易写错的地方。两个 64 位数相加 `c = a + b`，如果溢出，`c` 会小于 `a`（无符号回绕）：

```cpp
uint64_t c = r.w[1] + lo;
uint64_t carry1 = (c < r.w[1]) ? 1ULL : 0ULL;
r.w[1] = c;
```

这个 `c < r.w[1]` 就是进位标志。它等价于 x86 的 `add` 指令自动设置的 CF 位，但在 C++ 里不能直接读 CF，只能用这种无符号回绕检测。编译器会把它识别成条件传送（cmov），不会真的分支。

第二段更复杂，因为要加三个东西：

```cpp
uint64_t c2 = r.w[2] + hi + carry1;
r.w[2] = c2;
r.w[3] = (c2 < r.w[2] + carry1) ? 1ULL : 0ULL;
```

这里 `r.w[2] + carry1` 是中间值，`c2` 如果比它小，说明 `hi` 加进去又溢出了，再进位到 `w[3]`。这个比较的写法很微妙：不能直接比 `c2 < r.w[2]`，因为 `carry1` 已经加进去了，中间值是 `r.w[2] + carry1`，不是 `r.w[2]`。

## mul：完整 256×256

`mul(a, b)` 是通用大整数乘法，双重循环：

```cpp
for (int i = 0; i < 4; ++i) {
    uint64_t carry = 0;
    for (int j = 0; j < 4 - i; ++j) {
        mul64(a.w[i], b.w[j], lo, hi);
        uint64_t s = r.w[i+j] + lo + carry;
        uint64_t c1 = (s < r.w[i+j]) ? 1ULL : 0ULL;
        uint64_t c2 = (s < lo) ? 1ULL : 0ULL;
        r.w[i+j] = s;
        carry = hi + c1 + c2;
    }
}
```

这是 Schoolbook 的标准展开：a 的第 i 字乘 b 的第 j 字，结果落到 r 的第 i+j 字。`j < 4 - i` 是因为高字乘高字会超过 256 位，截断丢弃（`mul` 只返回低 256 位）。

进位检测这里用了**双进位**：`s = r.w[i+j] + lo + carry`，`s < r.w[i+j]` 说明加 `lo` 溢出，`s < lo` 说明加 `carry` 又溢出。两个进位加起来再加上 `hi`，就是下一字的输入进位。这种三数相加的进位检测比两数复杂，容易漏一个分支。

## 小整数算术

### inc()

原地加 1：`w[0] += 1;`，然后从 `w[0]` 往 `w[3]` 检查：如果 `w[i]` 变成 0 了，说明进位到 `w[i+1]`，`w[i+1] += 1`。一旦某个字不是 0，进位链终止。这个函数在 dec128 舍入的"系数末尾加 1"场景里用。

### add_small(v)

原地加一个 64 位小整数。先 `w[0] += v`，检测进位，然后进位沿 `w[1]→w[3]` 传播。用于 `from_dec_string` 逐字符解析（每步加一个十进制数字）。

### mul_small(m)

原地乘一个 64 位小整数，返回溢出进位。从 `w[0]` 往 `w[3]` 逐字 `mul64(w[i], m, lo, hi)`，把上一步的 `hi`（进位）加到当前 `lo`，如果 `lo` 因为加进位而溢出，`hi` 再加 1。这个函数是 `from_dec_string` 的核心（每步 `mul_small(10)` 移位十进制）。

### div10()

原地除以 10，返回余数。dec128 规范化的热路径。从最高字 `w[3]` 到最低字 `w[0]` 逐字处理。关键常数：

```
2^64 / 10 = 0x1999999999999999
2^64 % 10 = 6
```

因为 `2^64 = 10 * 0x1999999999999999 + 6`。当高一位已经算出余数 `rem` 时，当前字 `w[i]` 实际代表的数是 `rem * 2^64 + w[i]`。除以 10：

```cpp
uint64_t q = w[i] / 10;
uint64_t r = w[i] % 10;
q += rem * 0x1999999999999999ULL;
r += rem * 6ULL;
q += r / 10;
r %= 10;
w[i] = q;
rem = r;
```

这个技巧叫"多精度除以单精度"（short division），和手工竖式除法一模一样：从高位到低位，每次带着上一位的余数除当前位。除数 10 是常数，编译器会把 `w[i] / 10` 和 `w[i] % 10` 优化成乘法+移位（不真的调用除法指令），所以很快。

返回值是最终余数，也就是整个 256 位数除以 10 的余数。这个余数在 dec128 舍入里决定最后一位十进制数字是 0 到 9 中的哪个，进而决定就近舍入时该进还是该舍。

### div_small(d)

通用小整数除法，除数可以是任意非零 64 位数。实现是逐位试商：对每个字的 64 位，从最高位到最低位逐 bit 处理，维护余数 `rem`，每步 `rem = rem*2 + bit`，如果 `rem >= d` 就 `rem -= d` 并置商位。每字 64 次 bit 迭代，四字共 256 次循环，比 `div10` 慢一个数量级，但通用。

## 比较与位工具

`cmp(o)` 从 `w[3]` 往 `w[0]` 逐字比，第一个不同的字决定大小，返回 -1/0/+1。`eq/lt/gt/le/ge` 是 cmp 的便捷包装。

`ge(v)`（v 是 64 位数）是个优化版：高三个字任一非零，说明这个数至少是 2^64，必然大于 64 位数 v；否则只看 `w[0]`。这个函数在 dec128 规范化循环里用：只要系数还大于等于 10^33，就继续除以 10。

`bit_length()` 用 `__builtin_clzll`（Count Leading Zeros）找最高字的最高位位置，返回位数。零返回 0。

## 移位

`shr(n)` 逻辑右移 n 位：`n/64` 个字整体搬走，剩下的 `n%64` 位跨字拼接——`r.w[i] = w[i+limbs] >> bits;`，如果 `bits` 非零，再从下一字高位补位 `r.w[i] |= w[i+limbs+1] << (64 - bits);`。`shl(n)` 对称。n≥256 返回零；n≤0 返回自身。

## 字符串互转

`to_string()` 是 `div10` 的反复应用：反复 `div10()` 把十进制位从低到高吐到一个 80 字节缓冲区尾部，然后返回反转切片。256 位最多 78 位十进制数字（2^256 ≈ 1.16×10^77），80 字节够。

`to_hex_string()` 更简单：四字按 `w[3]→w[0]` 顺序每字 16 个 hex nibble 直接拼 64 字符，然后剥前导零。修过一个 word 顺序 bug：早期版本把 `w[0]` 放最左，导致 hex 串读反，后来改为 `w[3]` 在最左（大端显示，符合人类阅读习惯）。

`from_dec_string(s)` 是 `to_string` 的逆：逐字符 `mul_small(10) + add_small(digit)`，遇到非数字字符停。

## 自由函数运算符

```cpp
UInt256 a(12345), b = UInt256::mul128(lo, hi, lo, hi);
a += b;
UInt256 c = a + b;
UInt256 d = a * b;
if (a > b) { ... }
```

`operator+`、`operator+=`、`operator*`（走 `mul`）全给。没有 `-`/`-=`/`/`（减法和通用大除法按需再补，目前 dec128 行走器用不到）。

## 为什么不用 Karatsuba 或 FFT

256 位乘法如果用 Karatsuba，可以把 4 次 `mul64` 降到 3 次（递归展开）。但 256 位太小了：Karatsuba 的递归开销（额外的加法、减法、临时变量）在 n=4 时反而比 Schoolbook 慢。n 到 16 字以上 Karatsuba 才开始划算，n 到 100 字以上 Toom-Cook 才值得考虑，FFT（Schönhage-Strassen）要到几千位才有用。

这个项目的 256 位乘法每步只跑一次，dec128 参考步数约 71 万量级。纯 `mul128` 层每次约 30 条指令、约 2130 万条指令量级，对应纯乘法周期约数秒量级。这**不含**每步的 `div10` 规范化、舍入、显示与线程调度；Dec128(BID) 的端到端实测耗时见 BASELINE_CN.md（十秒量级）。若换 Karatsuba，纯乘法层每次可能省数条指令，但 n=4 字时递归额外加减与临时变量的开销抵消收益，代码复杂度却翻倍，调试成本远超这点节省。

## 性能特征

在 i7-6700（Skylake，支持 ADX）上，`mul64` 编译后大约是：2 条 mov 拆高低 32 位、4 条 32×32→64 imul、3 条加法拼中间项、2 条位运算拼 lo/hi。总共约 11 条指令，延迟 3 个周期，吞吐量每周期 1 条（因为 imul 是流水线的）。

`mul128` 调 4 次 `mul64`，加上进位传播，约 40 条指令、约 15 个周期延迟。`mul`（256×256）双重循环 10 次 `mul64`，约 110 条指令、约 40 个周期延迟。

如果编译时用 `-O0`，编译器不会折叠 32 位乘法链，会真的生成 32 位 imul 指令序列，速度大约慢 3-5 倍。这就是为什么正式构建走 `-O2`，只有实验对照时才 `-O0`。

## 和 BID/DPD 的关系

UInt256 只服务于 BID 路线的 dec128。DPD 路线不用大整数——DPD 把系数存成 `std::vector<int>` 十进制数字数组，逐位乘法+进位，不需要二进制大整数。两条路线独立：BID 走二进制整数乘法（需要大整数），DPD 走十进制数字数组逐位乘加（不依赖二进制大整数）。

实测下来，DPD128 比 BID Dec128 还快，因为 UInt256 的 Schoolbook 乘法虽然用了硬件乘法器，但每次乘法的延迟还是比 DPD 的逐位十进制乘法（查表+一位加法）高。这反过来印证了：在 110 位这个量级，大整数乘法不一定比十进制数组快。

## 自测

`tests/tmp/uint_selftest.cpp` 是 10 项断言的独立 self-test：mul64 对照 `__int128` 验证、mul128 已知值验证、div10 余数验证、add_small 进位链验证、shr/shl 往返验证、to_string/from_dec_string 往返验证、cmp 顺序验证、bit_length 边界验证、mul_small 溢出进位验证、零值行为验证。全过后打印 `UINT_SELFTEST OK`。

## 局限性

- **没有符号位**：纯无符号。dec128 的符号存在 BID 位串的最高位，不放在 UInt256 里。
- **没有减法、没有通用大除法**：按需再补。
- **`mul` 截断低 256 位**：256×256 的高 256 位丢弃。对 dec128（110×110=220 位）够。
- **`div_small` 是逐位试商**：比 `div10` 慢，但通用。
- **依赖 `__builtin_clzll`**：GCC/Clang 专属，MSVC 不支持（项目本就排斥 MSVC）。
- **没有赋值运算符重载**：用默认拷贝构造，四个 64 位拷贝很便宜。
