# ea-FRDT 诞生记

## 一、起点：一个无聊的下午

2026 年秋天，一个很普通的下午。我在调试一个浮点计算的边界问题——某个数值在某个奇怪的点突然变成了 infinity，而我明明算的是 1.0 乘 1.02 这种简单到不能再简单的乘法。我写了个脚本，从 1.0 开始，每次乘 1.02，打印每一步的结果，直到溢出。

脚本很简单，大概二十行 Python。跑起来，看着数字一步步变大，从 1 到 10，到 100，到 1e10，到 1e20，最后在第 4481 步变成了 inf。我盯着那个 4481 看了很久。

然后我想：如果我换一种格式呢？比如 float16？比如 bfloat16？比如那个几乎没人用的 80 位 x87 扩展精度？

这个想法就是 ea-FRDT 的种子。

最初的版本真的很丑。一个 C 文件，main 函数，一个 for 循环，一个 printf。从 1.0 乘 1.02 到溢出，打印步数。大概五十行代码。我跑了 float、double、long double，看它们分别走多少步。

然后我发现了一个有意思的事：float 走 4481 步，double 走 8275 步，long double（80 位 x87）走了 573521 步。这个数字差距太大了——不是因为 long double 更精确所以走得远，而是因为它的指数范围更大。float 的指数是 8 位，最大大概 3.4e38；double 是 11 位，最大 1.8e308；long double 是 15 位，最大 1.2e4932。从 1.0 乘 1.02，要乘多少次才能到 1e4932？答案是 573521 次。

我把这个数字记了下来。那是第一个"基准"。

## 二、膨胀：从一种格式到十七种

最初的脚本只测 float 和 double。但我很快就不满足了。

我开始加格式。先是 float16——那个在 GPU 和深度学习里很流行的 16 位半精度。然后是 bfloat16——Google 在 TPU 里用的那个 16 位格式，指数位宽和 float32 一样，尾数位少。然后是 tf32——NVIDIA A100 里的那个 19 位格式。

每加一种格式，我就要写一段代码，模拟那种格式的位操作。float16 的指数是 5 位，尾数 10 位；bfloat16 指数 8 位，尾数 7 位。我不能用硬件 float16——不是所有 CPU 都支持——所以我用整数寄存器自己模拟：把浮点数拆成符号位、指数位、尾数位，在整数寄存器里移位、掩码、加减。

这就是"自写位级仿真"的起点。

然后是 fp8——那个在大模型训练里很火的 8 位浮点。有两种：E4M3（4 位指数，3 位尾数）和 E5M2（5 位指数，2 位尾数）。我把它们也加了进来。fp4 和 fp6 是更极端的——4 位和 6 位的浮点，几乎只能存 0 和 1 附近的数。

到这一步，我已经有了 9 种二进制浮点格式：fp4、fp6、fp8-e4m3、fp8-e5m2、float16、bfloat16、tf32、float32、float64。代码从五十行膨胀到了五百行。

但我还不满足。

## 三、深坑：x87 和 fp128

80 位 x87 扩展精度是个奇怪的东西。它不是 IEEE 754 标准的——它是 Intel 在 1980 年为 8087 协处理器设计的。80 位：1 位符号，15 位指数，64 位尾数。比 double 多了 3 位指数和 52 位尾数。

问题是：现代 CPU 上的 x87 指令是微码实现的，不是硬连线。而且编译器默认不用 x87 做主浮点运算——x86-64 模式下默认用 SSE2。我想测 x87，但我不想依赖硬件 x87——万一在一个没有 FPU 的嵌入式 ARM 上跑呢？

于是我决定：纯软件模拟 x87。把 80 位拆成三个整数：符号位、15 位指数、64 位尾数。在普通 64 位整数寄存器里做移位、掩码、加法。这不是为了快——纯软件模拟肯定比硬件慢——而是为了可移植。

然后是 fp128——128 位浮点，15 位指数，112 位尾数。IEEE 754-2008 定义了它，但几乎没有硬件实现。GCC 有个 libquadmath 库提供 __float128，但那是个第三方依赖。我不想加第三方依赖。

于是我又决定：纯软件模拟 fp128。112 位尾数意味着乘法中间结果要 224 位。64 位整数寄存器放不下 224 位，我需要用四个 64 位字拼起来做 schoolbook 乘法。这是我写过的最痛苦的代码之一——224 位乘法，逐位乘、逐位加、处理进位。

x87 和 fp128 的步数都是 573521——因为它们的指数范围一样。这个数字我记了很久。

## 四、十进制：BID 和 DPD

到这里，我已经有了 11 种二进制浮点格式。但浮点不只有二进制。

IEEE 754-2008 加了十进制浮点：decimal32、decimal64、decimal128。十进制浮点在金融计算里很重要——因为人类用十进制，二进制浮点在 0.1、0.2 这种数上有舍入误差，十进制浮点没有。

十进制浮点有两种编码方式：BID（Binary Integer Decimal）和 DPD（Densely Packed Decimal）。

BID 把系数当二进制整数存。比如 decimal64 的系数是 16 位十进制数字，你把它当一个 53 位的二进制整数存。乘法就是普通的二进制整数乘法，然后除以 10^n。

DPD 把系数当十进制数字串存。三个十进制数字（000-999）压缩成 10 位二进制（因为 10^3=1000 < 1024=2^10）。乘法就是逐位十进制乘法，然后做进位传播。

我先做了 BID。decimal32 的系数是 7 位十进制数字，用 23 位二进制整数存——很简单。decimal64 是 16 位，用 53 位整数——也还行。但 decimal128 是 34 位十进制数字——这需要 113 位的二进制整数。64 位寄存器放不下。

这就是 UInt256 的由来。

我写了一个纯软件的 256 位无符号大整数类，用四个 64 位字实现。schoolbook 乘法——像小学生做乘法一样，逐位乘、逐位加、处理进位。没有用 __int128——虽然 GCC/Clang 有 __int128，但我想要一个不依赖编译器专有扩展的纯 C++ 实现。

UInt256 写了很久。乘法、除法、加法、比较——每个操作都要仔细处理进位和移位。最后 decimal128 走 714521 步到溢出。

然后我做了 DPD。DPD 的三元组编解码是个查表——三个十进制数字压缩成 10 位，反过来解压。比 BID 简单，但十进制逐位乘法比 BID 的二进制整数乘法慢——因为十进制没有硬件乘法指令，你得逐位乘、逐位加进位。

DPD128 走了 714521 步——和 BID decimal128 一样，因为数学是一样的，只是编码不同。

到这一步，我有了 17 种格式：11 种二进制 + 6 种十进制（3 个 BID + 3 个 DPD）。

## 五、并发：多线程压测

单格式走路很慢。decimal128 要跑 13 秒，x87 要跑 4 秒。如果我想一次跑完所有格式，单线程要等很久。

于是我加了多线程。-m all 模式：起 N 个 worker 线程，每个线程独立跑完整的格式链。线程之间不共享状态——每个线程有自己的当前值、自己的步数、自己的结果。

这里有几个关键决策：

**绑核。** 每个 worker 绑到一个 CPU 核心上。Windows 用 SetThreadAffinityMask，Linux 用 pthread_setaffinity_np。不绑核的话，操作系统调度器会在核心之间迁移线程，导致性能抖动。绑核后，每个 worker 固定在一个核心上跑，不会被迁移。

**alignas(64)。** 每个 worker 的状态结构对齐到 64 字节——CPU 缓存行的标准大小。如果两个 worker 的状态落在同一个缓存行上，它们会互相 invalidate 对方的缓存（伪共享，false sharing），导致性能骤降。alignas(64) 把每个 worker 撑到一个完整的缓存行，消除伪共享。

**enum switch 分发。** 最初我用 std::function 存每个格式的步函数，然后 worker 循环里调 std::function。但 std::function 的调用开销很大——它要做类型擦除、间接调用、不能内联。我重写成了 enum FmtId + switch 直接分发。编译器可以把每个格式的步函数内联到 switch 的 case 里，零间接调用开销。

## 六、打磨：那些小坑

项目长大之后，开始出现各种小问题。

**步数不一致。** 有一次我改了代码，float32 的步数从 4481 变成了 4480。我排查了很久，发现是某个边界条件处理错了——当数字刚好在两个浮点数之间时，舍入方向选错了。我修了舍入逻辑，步数回到 4481。

**中文界面。** 我加了中英双语支持。所有用户可见的字符串都走 lang.h 的 tr() 函数，一个中文一个英文。这个决策后来被证明很重要——因为我打算开源，国际用户看不懂中文。

**Ctrl+C 处理。** 多线程模式下，Ctrl+C 要能正确中断所有 worker。Windows 用 SetConsoleCtrlHandler，Linux 用 signal。我花了点时间才把跨平台的信号处理写对。

**DPD 警告弹窗。** DPD 格式很慢——纯软件十进制逐位乘法，比 BID 慢 20-30 倍。如果用户不小心在 -m all 里加了 DPD，他的电脑会满载跑很久。我加了一个确认弹窗：启动前弹黄色警告，按 y 继续，10 秒不操作自动取消。后来 dec128 也加了同样的警告——因为 UInt256 大整数乘法也要跑 13 秒。

**输入安全。** 有用户（其实就是我自己）输入了一个恶意的 hex 字符串，带 ANSI 转义字符，导致终端被清空、颜色被篡改。我加了 sanitize() 函数，所有用户输入回显前过滤掉 ESC、C0 控制字符、DEL。hex 字符串限 32 个字符（128 位上限），非十六进制字符直接拒绝。

## 七、编译器之争：GCC vs Clang

项目最初用 GCC 编译。但 g++ 16.2.0 在这台机器上有个内部编译器错误（ICE）——编译到某个模板实例化时崩溃了。我试了各种 flag，都绕不过去。

然后我换了 Clang。MSYS2 里有两个 Clang：ucrt64 的 Clang 和 clang64 的 Clang。ucrt64 的 Clang 是 GCC 生态的兼容层，用 GNU ld 链接器，不支持 thin LTO。clang64 的 Clang 是 LLVM 原生的，自带 lld 链接器，支持 thin LTO。

用 clang64 编译，加 -Oz -flto=thin -ffunction-sections -fdata-sections -Wl,--gc-sections，产物从 3.3MB 降到了 0.81MB。这是因为 thin LTO 让编译器在链接时做跨模块优化，gc-sections 去掉了没被调用的函数。

我还试过 -march=native、-march=x86-64-v2、-march=x86-64-v3。反汇编发现，-march=native 在这台 i7-6700 上生成了 5 条 mulx 指令（BMI2 的无进位乘法），但没有 adcx/adox（ADX 的双进位链）——因为 i7-6700 是 Skylake，不支持 ADX。要双进位链得换 Broadwell 以后的 CPU。

## 八、开源准备

项目到 0.81MB、17 种格式、多线程、双语、输入加固、基准测试，我觉得可以开源了。

但开源前我做了一件事：想象公开后 72 小时会发生什么。

稀缺标签——fp128、decimal-float、bid-decimal、dpd-decimal、x87-emulation、uint256——这些标签在 GitHub 上几乎没有项目。搜索结果会直接顶到第一页。硬核 README——"面向硅片魔鬼高压硬件测试"——打中编译器开发者、微架构调试者、金融审计三类人。炸裂仓库名——ea-FRDT——有传播性。

三者叠加，72 小时内会有流量海啸。我准备了：

- Issue 模板（问题、编译问题、bug 报告）
- PR 模板（checklist：零警告、smoke test、英文注释）
- CI（GitHub Actions，Ubuntu 上 GCC + Clang 双 job）
- README 加 Windows-only 警告、MSVC 不支持、编译器要求
- Limitations 自曝章节（__int128 残留、DPD 排除、无 GPU）
- Disclaimer 免责声明（满载可能死机、降频、硬件磨损）
- MIT 许可证
- CMakeLists.txt
- SECURITY.md、CHANGELOG.md、CONTRIBUTING.md

## 九、这个项目是什么

ea-FRDT 不是一个基准测试。它不报 GFLOPS，不跟 SPEC CPU 比，不跟 MLPerf 比。

它是一个走路工具。它从一个数出发，按固定步长走，一步一步，直到那个格式再也表示不了这个数。它打印第几步、什么 hex 位型、走了多少毫秒。

它的价值在于：当你在验证一个编译器优化 pass 有没有破坏精度、调试一个 CPU 浮点单元有没有 bug、审计一个金融十进制管道有没有舍入误差时，你需要知道——从 1.0 乘 1.02，float32 在第 4481 步溢出，float64 在第 8275 步，x87 在第 573521 步，decimal128 在第 714521 步。

这些数字不是拍脑袋的。它们是数学事实。不管你用 i7-6700 还是 Fugaku 超算，float32 从 1.0 乘 1.02 到溢出永远是 4481 步。CPU 决定速度，不决定结果。

## 十、写在最后

这个项目从一个无聊的下午开始，从二十行 Python 脚本开始，从一个"如果我换 float16 会怎样"的问题开始。它长成了 0.81MB 的 C++23 程序，支持 17 种浮点格式，多线程压测，中英双语，纯软件大整数乘法，绑核缓存行隔离。

它不完美。UInt256 还不是最优的——schoolbook 乘法可以换成 Karatsuba 或 Toom-Cook。x87 和 fp128 还残留 __int128 辅助。DPD 的 declets 串联子单元还是技术债。没有 GPU offload。没有 WebAssembly 目标。

但它是对的。每一步都是确定性的。每个 hex 位型都是可审计的。每个退出原因都是可解释的。

这就是 ea-FRDT。面向硅片的魔鬼高压硬件测试。

算法本身可能会开小差。
