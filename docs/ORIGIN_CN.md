# ea-FRDT 诞生记

> 说明：本文是项目成长史叙事，记录早期原型的设计动机与决策；文中早期原型的粗步数、早期机器耗时仅为历史参考，当前构建的权威参考步数与耗时以 BASELINE_CN.md 为准，实现细节以源码为准。

## 一、起点：一个无聊的下午

2026 年秋天，一个很普通的下午。我在调试一个浮点计算的边界问题——某个数值在某个奇怪的点突然变成了 infinity，而我明明算的是 1.0 乘 1.02 这种简单到不能再简单的乘法。我写了个脚本，从 1.0 开始，每次乘 1.02，打印每一步的结果，直到溢出。

脚本很简单，大概二十行 Python。跑起来，看着数字一步步变大，从 1 到 10，到 100，到 1e10，到 1e20，最后在第 4481 步附近看到了上溢。我盯着那个数字看了很久。

然后我想：如果我换一种格式呢？比如 float16？比如 bfloat16？比如那个几乎没人用的 80 位 x87 扩展精度？

这个想法就是 ea-FRDT 的种子。

最初的版本真的很丑。一个 C 文件，main 函数，一个 for 循环，一个 printf。从 1.0 乘 1.02 到溢出，打印步数。大概五十行代码。我跑了 float、double、long double，看它们分别走多少步。

然后我发现了一个有意思的事：不同格式从 1.0 乘 1.02 走到溢出的步数差距极大（早期原型粗记：float 约 4481、long double 达数十万；当前构建参考步数见 BASELINE_CN.md）。差距大的主因不是 long double 更精确，而是它的指数范围更大。float 指数 8 位、最大约 3.4e38；double 11 位、约 1.8e308；x87 15 位、约 1.2e4932。指数位宽决定可达上限，也就决定要乘多少步才到溢出边界。

我把这个量级记了下来。那是第一个"基准"。

## 二、膨胀：从一种格式到十七种

最初的脚本只测 float 和 double。但我很快就不满足了。

我开始加格式。先是 float16——那个在 GPU 和深度学习里很流行的 16 位半精度。然后是 bfloat16——Google 在 TPU 里用的那个 16 位格式，指数位宽和 float32 一样，尾数位少。然后是 tf32——NVIDIA A100 里的那个 19 位格式。

每加一种格式，我就要写一段代码，模拟那种格式的位操作。float16 的指数是 5 位、尾数 10 位；bfloat16 指数 8 位、尾数 7 位。我不能只依赖硬件 float16——不是所有 CPU 都支持——所以我用整数寄存器自己模拟：把浮点数拆成符号位、指数位、尾数位，在整数寄存器里移位、掩码、加减。

这就是"自写位级仿真"的起点。

然后是 fp8——那个在大模型训练里很火的 8 位浮点。有两种：E4M3（4 位指数，3 位尾数）和 E5M2（5 位指数，2 位尾数）。我把它们也加了进来。fp4 和 fp6 是更极端的——4 位和 6 位的浮点，几乎只能存 0 和 1 附近的数。

到这一步，我已经有了 9 种二进制浮点格式：fp4、fp6、fp8-e4m3、fp8-e5m2、float16、bfloat16、tf32、float32、float64。代码从五十行膨胀到了五百行。

但我还不满足。

## 三、深坑：x87 和 fp128

80 位 x87 扩展精度是个奇怪的东西。它不是 IEEE 754 标准的——它是 Intel 在 1980 年为 8087 协处理器设计的。80 位：1 位符号，15 位指数，64 位尾数。比 double 多了 3 位指数和 16 位尾数。

问题是：现代 CPU 上的 x87 指令多为微码实现，而且 x86-64 模式下编译器默认用 SSE2 而非 x87。我想测 x87，但不想依赖硬件 x87——万一在一个没有对应 FPU 的环境上跑呢？

于是我决定：纯软件模拟 x87。把 80 位拆成符号、15 位指数、64 位尾数，在普通 64 位整数寄存器里做移位、掩码、加法。这不是为了快——纯软件模拟肯定比硬件慢——而是为了可移植与结果确定。

然后是 fp128——128 位 binary128，15 位指数，112 位尾数。IEEE 754-2008 定义了它，但几乎没有硬件实现；GCC 的 libquadmath 提供 `__float128`，但那是第三方依赖，我不想引入。

于是我又决定：纯软件模拟 fp128。112 位尾数意味着乘法中间结果需要更宽的积；64 位整数寄存器放不下，需要多个 64 位字拼起来做 schoolbook 乘法，逐位乘、逐位加、处理进位。这是我写过的最痛苦的代码之一。

x87 与 fp128 都要走到各自很大的指数上限，步数在同一量级；二者尾数宽度不同、并非同一位宽实现，具体参考值以 BASELINE_CN.md 为准。这个量级我记了很久。

## 四、十进制：BID 和 DPD

到这里，我已经有了 11 种二进制浮点格式。但浮点不只有二进制。

IEEE 754-2008 加了十进制浮点：decimal32、decimal64、decimal128。十进制浮点在金融计算里很重要——因为人类用十进制，二进制浮点在 0.1、0.2 这种数上有舍入误差，十进制浮点没有。

十进制浮点有两种编码方式：BID（Binary Integer Decimal）和 DPD（Densely Packed Decimal）。

BID 把系数当二进制整数存。乘法就是普通的二进制整数乘法，再按 10^n 调整指数。DPD 把系数当十进制数字串存：三个十进制数字（000–999）压缩成 10 位二进制（因为 10^3=1000 < 1024=2^10），乘法逐位十进制进行、再做进位传播。

我先做了 BID。decimal32 系数位数少、很简单；decimal64 适中；decimal128 有 34 位十进制数字，需要很宽的二进制整数，单个 64 位寄存器放不下。

这就是 UInt256 的由来：纯软件 256 位无符号大整数，四个 64 位字，schoolbook 乘法；UInt256 本身不使用 `__int128`，以保持可移植。

UInt256 写了很久：乘法、除以 10、比较、取低位，每个操作都要仔细处理进位。Dec128 的参考步数在七十万量级（当前参考值见 BASELINE_CN.md）。

然后我做了 DPD。DPD 的单 declet 编解码是查表——三个十进制数字压缩成 10 位、反向解压；比 BID 的大整数更直接，但十进制逐位乘法没有硬件乘法器，需逐位乘加进位。DPD 与 BID 的数学值一致，只是位编码不同；多 declet 串联的 pack/unpack 子单元后来补齐，并带启动往返自检。

到这一步，我有了 17 种格式：11 种二进制 + 6 种十进制（3 个 BID + 3 个 DPD）。注意：`-m all` 默认链是 17 选 13，DPD×3 与 Dec128 默认排除、需 `--only` 显式加入。

## 五、并发：多线程压测

单格式走路较慢。早期机器上 decimal128 曾跑十秒量级、x87 数秒量级（耗时随机器、优化级别与构建差异很大，参考值见 BASELINE_CN.md）。如果想一次跑完，单线程要等很久。

于是我加了多线程。`-m all` 模式：起 N 个 worker 线程，每个线程独立跑格式链。线程之间不共享状态——各自的当前值、步数与结果。

这里有几个关键决策：

**绑核。** 每个 worker 绑到一个逻辑核（核心编号 0-based）。Windows 用 `SetThreadAffinityMask`，并额外把该线程设为 `THREAD_PRIORITY_TIME_CRITICAL`；Linux 用 `pthread_setaffinity_np` + `CPU_SET`，不设置实时优先级。不绑核的话，调度器会在核心之间迁移线程，导致性能抖动。

**alignas(64)。** 每个 worker 的状态结构对齐到 64 字节——CPU 缓存行常见大小。若两个 worker 的状态落在同一缓存行，会互相 invalidate（伪共享，false sharing），性能骤降；`alignas(64)` 把每个 worker 撑到一个完整缓存行，消除伪共享。

**enum switch 分发。** 最初我用 `std::function` 存每个格式的步函数，在 worker 循环里间接调用；`std::function` 有类型擦除与间接调用开销、不利于内联。后来重写成 `enum FmtId` + switch 直接分发，编译器可把各格式步函数内联进 case。

## 六、打磨：那些小坑

项目长大之后，开始出现各种小问题。

**步数一致性。** 边界条件（恰好落在两个可表示数之间时的舍入方向）一旦写错，步数就会漂移；修对舍入逻辑后，同一系数与实现下步数保持确定。当前参考值以 BASELINE_CN.md 为准。

**双语界面。** 所有用户可见字符串走 `lang.h` 的翻译表，一份中文一份英文。这个决策后来被证明很重要——开源后国际用户看不懂中文；默认语言为 `zh`，`--lang en` 切换。

**Ctrl+C 处理。** 多线程模式下 Ctrl+C 要能正确中断所有 worker：置中断标志位、各 worker 优雅退出并给出双语提示，而不是硬杀。

**慢速格式确认门。** DPD 是纯软件逐位十进制乘法、较慢；Dec128 走 UInt256 大整数乘法也较慢。确认门仅在 `-m all` 出现：纳入 DPD32/64/128 或 Dec128 时触发二级红色 `[!!!]`；其他情形（如 `-l -1` 未配 `-t`、倍率过小）为一级黄色 `[!]`；10 秒内按 `y` 继续，否则打印 `cancelled` 并退出 0；单格式模式不弹此门。

**输入安全。** 用户输入回显前过滤 ESC、C0 控制字符、DEL；`0x` Raw 输入做合法性校验，畸形或越界直接以退出码 2 报错，避免终端被转义序列污染。

## 七、编译器之争：GCC vs Clang

项目支持 GNU/Clang 工具链，明确不支持 MSVC。早期 g++ 在本机某个模板实例化处遇到过内部编译器错误（ICE），切换到 Clang 规避。

MSYS2 的 Clang 中，clang64 是 LLVM 原生、自带 lld、支持 thin LTO；在 `-Oz -flto=thin` 配合函数/数据段分离与 `--gc-sections` 下，可显著缩小产物体积。优化与本机指令集（`-march=native` 对 `mulx`/ADX 的支持视具体微架构而定）是构建层面的取舍，不改变数值结果。

项目具备多格式覆盖、多线程、双语、输入加固与基线记录后，我开始整理开源材料：Issue 模板、CI（Ubuntu 上 GCC + Clang 构建并跑 smoke）、README 的平台与编译器说明、Limitations 自曝章节、免责声明、MIT 许可证（仓库根目录 LICENSE）、以及 SECURITY.md、CHANGELOG.md、CONTRIBUTING.md 等文档。

## 九、这个项目是什么

ea-FRDT 不是一个基准测试。它不报 GFLOPS，不跟 SPEC CPU 比，不跟 MLPerf 比。

它是一个走路工具：从一个数出发，按固定步长一步一步走，直到格式再也表示不了这个数；打印第几步、可选的 hex/bin 位型（`--bits`，默认关闭）与耗时。

它的价值在于：验证编译器优化 pass 是否破坏精度、调试 CPU 浮点单元行为、审计金融十进制管道舍入误差时，可对照固定系数 ×1.02 下各格式的参考步数（如 FP32 约 4481、Dec128 约七十万量级；完整表见 BASELINE_CN.md）。

在同一系数、同一实现与同一舍入规则下，步数是确定性的，不随机器改变——CPU 决定速度，不决定数值结果；但跨编译器、跨优化级别或切换步进模式时步数可能不同，因此以 BASELINE_CN.md 的当前参考值为准，不把单一机器测得的耗时或步数当成跨构建承诺。

## 十、写在最后

这个项目从一个无聊的下午、二十行 Python 脚本、一个"如果我换 float16 会怎样"的问题开始，长成了一个 C++23 程序：覆盖 17 种格式、支持多线程压测、中英双语、纯软件大整数乘法、绑核与缓存行隔离。

它不完美。UInt256 当前采用 n=4 字 Schoolbook 乘法，在该规模比 Karatsuba 划算，更宽系数或换算法时再评估；x87 与 fp128 的 64×64 尾数中间积借助 `unsigned __int128`（整数辅助，非 FPU 数据类型）；DPD 多 declet 串联 pack/unpack 子单元已补齐并带往返自检；没有 GPU offload，也没有 WebAssembly 目标。

但它是对的：每一步都是确定性的，位型可审计，退出原因可解释（`overflow`、`underflow`、`identity->stop`、`safety->limit`、`timeout`、`cancelled`、`interrupted`）。

这就是 ea-FRDT——面向硅片的魔鬼高压硬件测试。
