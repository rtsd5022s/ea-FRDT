# 测试工具的遮羞布与 ea-FRDT 的扒底裤

## 一、前言：为什么我们不信任浮点基准测试

每个写过数值代码的工程师都被教育过：浮点是不可靠的，不要直接比较两个浮点数，要加 epsilon。但很少有人追问：这个“不可靠”到底有多不可靠？从 1.0 开始乘 1.02，到底要走多少步才会碰到格式表示不了的数？是几千步还是几百万步？在这中间，哪一步会出现尾数进位溢出？哪一步会从正规数掉到次正规数？哪一步会突然跳到无穷大？

这些问题，传统基准测试一个都不回答。

SPEC CPU、MLPerf、Linpack、Geekbench、各种 GFLOPS 跑分软件，测量的是“在精心挑选的输入下，每秒能完成多少次运算”。它们告诉你 CPU 的吞吐率，不告诉你浮点格式的边界在哪里。它们给你一个分数对比两颗 CPU 的快慢，但不告诉你反复乘 1.02 时编译器优化选项会不会改变舍入路径，也不告诉你 DPD 和 BID 在同一个十进制数上是否给出一致的步数与位模式。

ea-FRDT 就是为了扒掉这层遮羞布而写的。它不跑分，它走路。它从一个值出发一步一步走，默认模式下每步打印当前值与（可选的）位模式，直到格式走不动——溢出到无穷、下溢到零、撞到 `safety->limit` 安全上限、身份无进展退出，或者你按了 Ctrl+C。它不报告 GFLOPS，它报告“FP32 在参考约第 4481 步达到溢出边界”。

## 二、传统基准测试的七块遮羞布

### 遮羞布一：只测吞吐率，不测边界

Linpack 测的是解线性方程组的速度，矩阵规模经过挑选以最大化缓存命中与 BLAS 优化路径，给出的 GFLOPS 在工程上与“各精度格式在边界附近的行为”关系不大。

SPEC CPU 的 fp 套件用真实负载（编译、推理、流体模拟），但输入固定、浮点值在健康区间游走，永远不会走到溢出附近。

ea-FRDT 直接从 1.0 走到 `+inf`，不挑输入、走完整条格式边界。参考步数（×1.02、该构建实测、见 BASELINE_CN.md）：FP32≈4481、Dec32/DPD32≈11279、FP64≈35843、Dec64/DPD64≈44767、x87/FP128 数十万、Dec128/DPD128 七位数。这些参考值是对照基线：不同实现若在同格式、同系数下系统性偏离，就值得排查舍入或进位实现。

### 遮羞布二：报告最好情况，隐藏最坏情况

跑分软件喜欢报告峰值 GFLOPS，那是向量长度刚好填满寄存器、数据命中 L1、无分支误判、无 cache miss 的理想情形；不少基准还在多次运行后取最好一次而非平均。

ea-FRDT 不挑最好情况，一次走到头。并发模式下多个 worker 各跑一条链，纯软件格式在算术正确时应给出一致的参考步数；步数一致验证确定性，差异（耗时而非步数）则反映缓存争用、调度抖动与热降频。

### 遮羞布三：不展示位模式

传统基准只给十进制表示，不告诉你内存里的 hex 位型、符号位、指数与尾数分布；出现微小误差时无法定位是哪一位变了。

ea-FRDT 用 `--bits hex|bin` 在每步追加位模式（`bin` 按 sign/exponent/coefficient 分组）。当 DPD 与 BID 对同一十进制数给出不同编码位型时，你看到的是编码层差异；`--dump` 还能把每条原始记录落盘、由 `dump_inspect.py` 用 CRC-32 对账。

### 遮羞布四：不区分编译器优化差异

同一段 C++ 在 `-O2` 与 `-O3` 下，FMA 收缩与向量化可能改变中间舍入，GCC 与 Clang 的 FMA 策略也不同。传统总分掩盖了这一点。

ea-FRDT 的自写位级格式（FP4/FP6/FP8E4M3/FP8E5M2/BF16/TF32）与纯软件档（x87、FP128、BID/DPD 十进制）在整数/数组上运算，不依赖 FPU 与 FMA 收缩；原生档 FP16/FP32/FP64 才使用编译器原生浮点类型。项目只支持受支持的 GNU/Clang 工具链（MSVC 被排除）。纯软件格式的数学结果在受支持工具链之间可对照；若步数变化，先查整数运算优化与舍入实现。

### 遮羞布五：十进制浮点被忽视

IEEE 754-2008 定义 Decimal32/64/128，编码分 BID 与 DPD，在金融、货币、会计中重要，因为二进制浮点表示不了 0.1。传统基准几乎不测十进制浮点。

ea-FRDT 把十进制放在核心位置：dec32/dec64/dec128 走 BID，另有 dpd32/dpd64/dpd128 走 DPD。BID 系数为二进制整数、Dec128 用纯 64 位字的 `UInt256` schoolbook 乘法；DPD 系数为十进制数组、逐 declet 编解码。Dec128(参考 714521 步量级) 这类数字在通用跑分里找不到。

### 遮羞布六：不展示下溢和次正规行为

溢出为人熟知，下溢到次正规数才是性能陷阱：尾数前补零、指数固定，许多 FPU 上的次正规运算为微码仿真、显著变慢。传统输入从不走到该区间。

ea-FRDT 支持 `-k <1` 递减、`-a max-finite` 从最大值往下走、`-s` 从最小子正规起点起步，可观察在哪一步由正规进入次正规、在哪一步掉到零；`-a min-normal` 则从最小正规数起步递增。

### 遮羞布七：单线程英雄主义，不展示多核争用

多数跑分只跑单线程或少量线程，不展示多线程压满时的调度反应、缓存争用与带宽饱和。

ea-FRDT 的并发模式 `-m all` 让每个 worker 绑一个逻辑核，独立跑默认 13 格式链（DPD×3 与 Dec128 默认排除，`--only` 加入）；`alignas(64)` 让 `WorkerSlot` 独占缓存行以消除伪共享。算术正确时各 worker 参考步数一致，steps/s 则可能因缓存争用与热降频低于单线程。

## 三、ea-FRDT 扒掉的五层底裤

### 底裤一：格式边界可被逐步行走，而非一句模糊范围

“FP32 范围约 3.4e38”是模糊描述；ea-FRDT 把从 1.0 × 1.02 到溢出的过程逐步走出来，参考步数见 BASELINE_CN.md（FP32≈4481、Dec64≈44767、x87/FP128 数十万、Dec128 七位数）。这些是可复现对照的基线，而非估计值。

### 底裤二：BID 和 DPD 是不同算法，不是同一件事

BID 把系数当二进制整数存，走二进制乘后按 10^n 调指数；DPD 把系数当十进制数字串存，逐位乘加进位、再经 declet 编解码。同一数在两种编码下位型不同；Dec128 的 BID 路径用 UInt256，DPD 路径用数字数组。

### 底裤三：纯软件浮点可行，不依赖硬件 FPU / libquadmath

x87 80 位与 FP128 binary128 全部在整数寄存器/数组上仿真：宽尾数乘法、移位、掩码、归一化与舍入，不使用 `long double`、`__float128` 或 libquadmath。这使 FP128/x87 可在无对应硬件 FPU 的受支持平台上以软件方式运行（慢但结果确定）。

### 底裤四：并发压测的价值是确定性复现，不是“越快越好”

多线程压测的目的不是榨 GFLOPS，而是验证在多核争用、缓存乒乓、调度漂移下参考步数仍一致。若某 worker 步数与其他不一致，需排查缓存行隔离、内存序或状态误读；一致的步数 + 波动的速度才是预期输出。

### 底裤五：安全防护是必要的，不是累赘

工具允许无限循环、递减、负起点与 Raw 起点，因此需要防护，且现有防护是“确认与警告”而非一律硬拒绝：

- `-l -1` 未配 `-t`：在 `-m all` 触发一级黄色 `[!]` 确认警告，建议配超时，10 秒内按 `y` 继续，否则 `cancelled`；并非禁止启动。
- 倍率异常：`0`/负/NaN/Inf 硬退出码 `2`；倍率 `< 1e-10` 仅在 `-m all` 给一级警告；真正兜底是 `safety->limit`（`2^120` 计数器）。
- 慢格式：纳入 DPD×3 或 Dec128(BID) 时，`-m all` 给二级红色 `[!!!]` 确认；单格式不弹门。
- Ctrl+C 置 `sigint` 标志，双语提示后优雅退出。

传统固定输入、固定步数的跑分不需要这些；本工具面向“走到边界”，防护是安全带。

## 四、ea-FRDT 不做什么

- 不测 GFLOPS，不报告每秒运算次数。
- 不比两颗 CPU 的快慢，只验证格式行为与参考基线是否对得上。
- 不测 GPU（不碰 CUDA/ROCm/Metal），是 CPU 工具。
- 不测 libm 的 sin/cos/sqrt 等超越函数精度，只覆盖乘/除类步进、溢出/下溢/舍入边界。
- 不做累计误差 epsilon 审计，只走到格式边界。
- 不做性能调优，只回答“格式在哪里断、走多少步”。

## 五、结语：工具应展示真相，而不是掩盖它

传统基准是哈哈镜：好看的分数来自挑选过的输入、最好情况、峰值吞吐、隐藏的位型、回避的下溢区间与单线程局限。ea-FRDT 是显微镜：逐步展示从 1.0 到边界的过程、BID/DPD 编码差异、次正规区间、多核争用与防护门。它不跑分，它走路；给出的参考步数（见 BASELINE_CN.md）是跨实现对照的基线。
