# 测试工具的遮羞布与 ea-FRDT 的扒底裤

## 一、前言：为什么我们不信任浮点基准测试

每个写过数值代码的工程师都被教育过：浮点是不可靠的，不要直接比较两个浮点数，要加 epsilon。但很少有人追问：这个"不可靠"到底有多不可靠？从 1.0 开始，乘 1.02，到底要走多少步才会碰到格式表示不了的数？是 4000 步还是 400 万步？在这中间，哪一步会出现尾数进位溢出？哪一步会从正规数掉到次正规数？哪一步会突然跳到无穷大？

这些问题，传统基准测试一个都不回答。

SPEC CPU、MLPerf、Linpack、 Geekbench、各种 GFLOPS 跑分软件，它们测量的是"在精心挑选的输入下，每秒能完成多少次运算"。它们告诉你 CPU 的吞吐率，不告诉你浮点格式的边界在哪里。它们给你一个分数，让你对比两颗 CPU 的快慢，但不告诉你当你把一个数反复乘 1.02 时，编译器的优化选项会不会让结果偏移三位小数，或者 DPD 和 BID 编码在同一个十进制数上会不会给出不同的十六进制位模式。

ea-FRDT 就是为了扒掉这层遮羞布而写的。它不跑分，它走路。它从一个值出发，一步一步走，每一步都打印当前值、当前步长、当前十六进制位模式，直到格式走不动了——溢出到无穷、下溢到零、撞到安全上限、或者你按了 Ctrl+C。它不报告 GFLOPS，它报告"在第 4481 步，FP32 溢出了"。

## 二、传统基准测试的七块遮羞布

### 遮羞布一：只测吞吐率，不测边界

Linpack 测的是解线性方程组的速度。它选的矩阵规模是精心调过的，让缓存命中率最高，让 BLAS 库的优化路径全部命中。它给你一个 GFLOPS 数字，这个数字在工程上几乎没有意义——因为现实中的数值计算不是解一个 10000 阶稠密矩阵，而是处理 17 种不同精度的浮点数在边界附近的行为。

SPEC CPU 的 fp 套件用的是真实负载，比如 gcc 编译、一个 AI 推理、一个流体模拟。但这些负载的输入都是固定的，浮点值在一个健康的区间里游走，永远不会走到溢出附近。你永远不会在 SPEC 的报告里看到"这个编译器在 FP64 的 2^1023 附近产生了错误的舍入"。因为 SPEC 不测那个区间。

ea-FRDT 直接从 1.0 走到 +inf。它不挑输入，它走完整个格式。FP32 从 1.0 乘 1.02 到溢出要走 4481 步，FP64 要走 8275 步，Dec64 要走 11958 步。这些数字本身就是基准——如果你的编译器、你的 libm、你的 FPU 在这些步数上和标准参考值不一致，你就知道哪里出了问题。

### 遮羞布二：报告最好情况，隐藏最坏情况

跑分软件喜欢报告峰值 GFLOPS。峰值是在向量长度刚好填满 AVX-512 寄存器、数据刚好在 L1 缓存里、没有分支预测失败、没有 cache miss 的情况下测出来的。现实世界中你永远达不到这个数字。

更虚伪的是，很多基准测试在多次运行后取最好的一次，而不是平均值。这意味着如果你的 CPU 因为散热降频了一次，跑分软件会忽略那次，只给你看最好看的数字。

ea-FRDT 不选最好情况。它从 1.0 走到 inf，每一步都算数。它不跑 100 次取最好，它只走一次，走到头为止。你看到的 4481 步就是 4481 步，不会因为 CPU 温度低一点就变成 4482 步。如果在并发模式下，8 个 worker 同时跑，你会看到不同核心上的步数完全一致——因为浮点格式是确定性的，只要算术正确，从 1.0 乘 1.02 到 inf 永远是 4481 步。任何偏差都是 bug。

### 遮羞布三：不展示位模式

传统基准测试给你的是一个浮点数的十进制表示，比如 `3.141592653589793`。它不告诉你这个数在内存里的十六进制是 `400921FB54442D18`，也不告诉你符号位是 0、指数是 0x400、尾数是 0x921FB54442D18。

这意味着当你的计算出现一个微小误差时，你只能看到十进制输出差了一点点，但你不知道是哪一位错了。是尾数最后一位进位了？是指数偏了 1？是符号位翻了？你只能猜。

ea-FRDT 的 `-x` 选项在每一步后面追加十六进制位模式。你可以看到 `x = 1.299e+00 (hex=3FA7D70A)` 这样的输出。当 DPD 和 BID 对同一个十进制数给出不同编码时，你看到的不是两个不同的十进制数，而是两个不同的 hex——这才是 IEEE 754 编码层面的真相。你可以精确地看到是哪一位在编码转换时变了。

### 遮羞布四：不区分编译器优化差异

同一段 C++ 代码，用 `-O2` 和 `-O3` 编译，浮点结果可能不同。因为 `-O3` 允许更激进的向量化和 FMA 融合，而 FMA 会改变中间舍入。GCC 和 Clang 对同一个表达式的 FMA 生成策略不同。MSVC 直接被很多跑分软件排除在外，因为它的浮点模型和其他编译器不一致。

但传统基准测试不会告诉你这些。它给你一个总分，这个总分是在某个特定编译器版本、某个特定优化级别下测出来的。换个编译器，分数可能差 30%，但你不知道为什么。

ea-FRDT 不依赖任何编译器的浮点行为——它的自写格式（FP4、FP6、FP8、BF16、TF32、x87、FP128、Dec128）全部是纯软件整数仿真。它不用 FPU，不用 FMA，不用 `long double`。它在整数寄存器里做移位、掩码、加法。这意味着不管你用 GCC、Clang、MSVC 还是一个随便什么编译器，从 1.0 乘 1.02 到 inf 的步数都是一样的。如果步数变了，那是你的编译器在整数优化上出了 bug，不是浮点的问题。

### 遮羞布五：十进制浮点被忽视

IEEE 754-2008 加了十进制浮点：Decimal32、Decimal64、Decimal128，有两种编码——BID（Binary Integer Decimal）和 DPD（Densely Packed Decimal）。这两种编码在金融计算、货币换算、会计系统里极其重要，因为二进制浮点表示不了 0.1。

但传统基准测试几乎不测十进制浮点。SPEC 没有 decimal 套件。Linpack 是纯二进制。MLPerf 是 GPU 上的 FP16/FP32。GCC 和 Clang 的 decimal 扩展（`__decimal32`）几乎没人用，libquadmath 的 decimal 支持也是后加的。

ea-FRDT 把十进制浮点放在核心位置。Dec32、Dec64、Dec128 各有 BID 和 DPD 两种实现。你可以对比 BID 和 DPD 在同一个数上的编码差异，看 DPD 的三元组编码在哪一位会触发前缀编码切换。Dec128 用自写的 UInt256 大整数乘法，不依赖 `__int128`，因为很多编译器不支持 128 位整数。你可以看到从 1.0 乘 1.02 走到 Dec128 溢出要 714521 步——这个数字在任何其他基准测试里都找不到。

### 遮羞布六：不展示下溢和次正规行为

溢出到无穷大家都知道，但下溢到次正规数才是真正的性能陷阱。当一个数小到正规格式表示不了时，它变成次正规数——尾数前面补零，指数固定在最小正规指数。次正规数的算术在很多 FPU 上是微码模拟，比正规数慢 10 到 100 倍。

传统基准测试不会让你走到次正规区间，因为那太慢了。它们的输入都是健康的正规数。

ea-FRDT 的 `-k 0.5` 从 max-finite 开始减半，一路穿过次正规区间走到零。你可以精确看到在哪一步正规数变成次正规数，在哪一步次正规数掉到零。你可以用 `-a min-normal` 从最小正规数开始，看它加 1 ULP 时是进位到下一个正规数还是停在次正规区间。这些行为在标准参考文档里有定义，但在实际硬件上是否一致，只有走一遍才知道。

### 遮羞布七：单线程英雄主义，不展示多核争用

绝大多数跑分软件是单线程的，或者最多开 4 个线程测并行效率。它们不展示当 8 个线程同时压满 8 个核心时，OS 调度器如何反应，缓存如何争用，内存带宽如何饱和。

ea-FRDT 的并发模式 `-m all` 把每个 worker 绑定到一个物理核心，每个 worker 独立跑完整套 17 种格式链。`alignas(64)` 把 worker 的状态结构撑到一个缓存行大小，消除伪共享。你可以看到 8 个 worker 同时跑时，每个 worker 的步数完全一致（因为算术是确定性的），但 steps/s 因为缓存争用而比单线程低。你可以看到 Windows 的 `SetThreadAffinityMask` 绑核后，worker 不会因为 OS 调度器漂移到其他核心。你可以看到 Ctrl+C 在多线程下是否能被正确捕获。

这些行为在传统跑分软件里完全看不到。

## 三、ea-FRDT 扒掉的五层底裤

### 底裤一：格式边界是精确的，不是模糊的

很多人以为 FP32 的范围是"大约 3.4e38"。这是一个模糊的描述。ea-FRDT 告诉你：从 1.0 乘 1.02 到 FP32 溢出，精确地走 4481 步。第 4480 步的值是 `337.856895e36`，第 4481 步就溢出了。这个数字不是估计，是走出来的。

同样，Dec64 从 1.0 乘 1.02 到溢出要 11958 步，x87 80 位要 573521 步，Dec128 要 714521 步。这些数字是格式的指纹——如果你在某个编译器、某个 FPU 上测出来不一样，你就知道哪里有问题。

### 底裤二：BID 和 DPD 是不同的算法，不是同一件事

很多人以为 BID 和 DPD 只是十进制浮点的两种打包方式，算术是一样的。这是错的。BID 把系数当二进制整数存，DPD 把系数当十进制数字串存。它们的乘除法在内部走完全不同的路径。BID 用二进制乘法加除以 10^n，DPD 用十进制数字乘法加进位传播。

ea-FRDT 同时实现了 BID 和 DPD，你可以直接对比。你会看到同一个十进制数在 BID 和 DPD 下的 hex 位模式不同——因为编码方式不同。你会看到 DPD 的三元组编码在系数跨越特定边界时，前缀位会从一种组合切换到另一种。你会看到 Dec128 的 BID 路径用 UInt256 做大整数乘法，而 DPD 路径用十进制数字数组做逐位乘法。

### 底裤三：纯软件浮点是可行的，不依赖硬件 FPU

很多人以为 x87 80 位和 binary128 必须靠硬件 FPU 或 libquadmath 才能算。ea-FRDT 证明了不是。x87 和 FP128 全部在整数寄存器里仿真：224 位整数乘法、移位、掩码、舍入。没有 `long double`，没有 `__float128`，没有 libquadmath。

这意味着你可以在任何有 C++23 编译器的平台上跑 FP128，不管那个平台的硬件 FPU 支不支持 128 位浮点。你可以在 ARM 上跑 x87 仿真。你可以在一个没有 FPU 的嵌入式芯片上跑完整套格式——虽然慢，但结果是正确的。

Dec128 的 UInt256 大整数乘法也是纯软件：schoolbook 乘法，4 个 64 位字乘 4 个 64 位字，移位累加进位。不依赖 `__int128`，因为很多编译器（特别是 MSVC 和 32 位目标）没有这个扩展。

### 底裤四：并发压测是确定性的，不是"越快越好"

很多人以为多线程浮点压测就是"开越多线程越快"。ea-FRDT 告诉你不是。当 8 个 worker 绑到 8 个核心同时跑时，每个 worker 的步数和单线程完全一致——因为浮点格式是确定性的，算术正确的话结果不依赖调度。你看到的不是"更快"，而是"同样的结果在更多核心上同时复现"。

这才是并发压测的真正目的：不是榨取 GFLOPS，而是验证在多核争用、缓存乒乓、调度漂移的环境下，浮点结果仍然一致。如果某个 worker 的步数和其他 worker 差了 1 步，那就是 bug——可能是缓存行共享导致的状态污染，可能是原子操作的内存序不对，可能是 worker 读到了其他 worker 的中间状态。

### 底裤五：安全防护是必要的，不是累赘

一个压测工具如果不小心写了 `-l -1`（无限循环）没配超时，它会把你的 CPU 烧到 100% 永不退出。ea-FRDT 拒绝这种组合。它在 factor 接近 1 时拒绝启动（因为那会走几百万步）。它在 DPD 和 dec128 启动前弹黄色警告让你确认。它在 Ctrl+C 时双语提示"程序提前退出"。它在无限循环必须配超时。

这些防护不是遮羞布，是安全带。传统跑分软件没有这些，因为它们只跑固定输入、固定步数、固定时间。ea-FRDT 让你可以无限走、递减、从负数开始、从 hex 位模式开始，所以它必须防护。

## 四、ea-FRDT 不做什么

为了不混淆，明确列出 ea-FRDT 不做的事：

- 不测 GFLOPS。它不报告每秒浮点运算次数，因为那个数字在边界测试里没有意义。
- 不比 CPU 快慢。它不比较 i7-6700 和 i9-13900K 的速度，它只验证浮点格式的行为是否正确。
- 不测 GPU。它是 CPU 工具，不碰 CUDA、ROCm、Metal。
- 不测数学库。它不测 libm 的 sin/cos/sqrt 精度，它只测加减乘和舍入。
- 不做数值精度审计。它不验证某个算法的累计误差是否在 epsilon 内，它只走到格式边界。
- 不做性能调优。它不告诉你如何让 FPU 跑得更快，它只告诉你浮点格式在哪里断。

## 五、结语：工具应该展示真相，而不是掩盖它

传统基准测试是一面哈哈镜。它给你一个好看的分数，但那个分数经过了精心挑选的输入、最好情况的运行、峰值吞吐的测量、位模式的隐藏、下溢区间的回避、单线程的局限。它让你觉得你的 CPU 很快，你的编译器很好，你的浮点没问题。

ea-FRDT 是一面显微镜。它把浮点格式从 1.0 到 inf 的每一步都摆给你看，把 BID 和 DPD 的编码差异摆出来，把次正规区间摆出来，把多核争用摆出来，把安全防护摆出来。它不跑分，它走路。它不给你一个好看的数字，它给你一串步数——4481、11958、573521、714521——这些数字就是浮点格式的真实指纹。

如果你在做编译器验证、微架构调试、十进制金融管道审计、或者只是好奇"从 1.0 乘 1.02 到底要走多少步才会溢出"，ea-FRDT 就是为这个写的。它不遮羞，它扒底裤。

算法本身可能会开小差。
